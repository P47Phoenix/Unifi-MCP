## 1. Problem Statement

A network operator who already administers UniFi gear has exactly two ways to ask a question about their own network today:

1. Click through the UniFi console UI, one page at a time, per site, per console.
2. Hand-roll `curl` against four separate developer APIs that share a vendor and share almost nothing else — three different pagination schemes (opaque cursor, offset/limit, and none at all), three different error envelopes, two different base hosts, a proxy path form that the vendor's own documentation contradicts itself on, and two specs that declare no authentication scheme whatsoever despite requiring one.

Neither path is conversational, and neither composes. "Which of my cameras went offline this week, and were any of them on the same switch port as a client that got blocked?" spans Protect, Network, and Site Manager, and there is no single surface that answers it.

Meanwhile the operator's LLM client (Claude Code, Claude Desktop) is already the place they think about their infrastructure. What is missing is a tool surface.

**Why now.** Ubiquiti has, as of 2026-08-01, published machine-readable OpenAPI specifications for all four APIs, plus per-service `llms.txt` flattened endpoint listings and `ai-gettingstarted.md` guides at a predictable URL pattern. The vendor has explicitly built for LLM consumption. The Cloud Connector — which reaches on-premises Network and Protect controllers through `api.ui.com` with no VPN — removes the last structural reason a tool like this had to live inside the LAN perimeter for cloud-reachable use cases. The raw material exists; the integration does not.

**Who has the problem.** Home-lab and prosumer operators running a single console, and multi-site administrators (MSPs, IT teams) running tens of consoles under an organization key. They have different topologies but the identical complaint: four APIs, one network, no unified way to ask.

**What we are building.** One MCP server. One credential story. One consistent tool surface over Site Manager, Network, Protect, and Mobility — all four, not a subset — reachable in cloud-direct, local-direct, and Cloud-Connector-proxied topologies, with the transport chosen by configuration rather than by calling different tools.

## 3. User Personas

### Primary: Dana — single-site home-lab owner

Runs one UniFi console (a Dream Machine class device) at home, on a private RFC1918 address, with the stock self-signed TLS certificate. Has a handful of Protect cameras, 40–80 clients, one site. Uses Claude Desktop on a laptop that is usually on the same LAN. Created an API key on the local console under Integrations. Does not have, and does not want, an organization. Does not use the Cloud Connector because the controller is one hop away.

**Key need:** ask questions about their own network in plain language, from the machine they are already sitting at, without a VPN, a reverse proxy, or a certificate authority. **Their blocker:** the self-signed certificate. Every naive HTTP client fails on their setup, and the "fix" that circulates on forums is to disable TLS verification globally, which is not acceptable as a default.

**What they will not tolerate:** a tool that reboots an access point because a model misread a sentence. Dana's network is their house.

### Primary: Marcus — multi-site MSP administrator

Administers 30–60 UniFi consoles across client sites under a single UniFi organization. Holds an organization API key created at `unifi.ui.com`. Has no VPN into most client networks and is not going to build one. Uses Claude Code from a workstation and increasingly from CI-adjacent automation. Cares about fleet-level questions ("which consoles are on firmware below X", "which sites have an offline device right now") far more than about a single client's DHCP lease.

**Key need:** reach on-premises Network and Protect controllers at client sites through the Cloud Connector, addressed by `consoleId`, without touching each site's LAN. **Their blockers:** discovering `consoleId` values in the first place, and the Connector's 100 requests/minute *per console* budget, which is the binding constraint on any fleet-wide sweep. A tool that fans out naively across 60 consoles will rate-limit itself into uselessness.

**Distinguishing constraint versus Dana:** Marcus lives in transport mode 3 (Connector) and organization-scoped keys; Dana lives in transport mode 2 (local direct) and an owner-scoped key. They exercise different code paths for the same tools, which is precisely why transport must be configuration, not a tool-selection decision.

### Secondary: Priya — cloud-only fleet reporter

Has Site Manager access and nothing else — no local console credentials, no interest in per-client detail. Wants inventory, host/console listings, ISP metrics, and device rollups for reporting. Site Manager keys are read-only today, which suits her exactly. She is the persona that proves the server must be *useful* with only a cloud key and zero host configuration.

**Key need:** minimal viable configuration — one API key, no host, no console ID, no TLS decisions — and a working tool surface.

**Serving path (added by ADR-05).** Priya is the persona for whom the stdio-only shape was the worst fit: everything she needs is cloud-reachable, so nothing in her use case required a process on her own machine, yet ADR-01 gave her no other option. She is now served two ways — the same local stdio install as everyone else, or a single-tenant self-hosted HTTP deployment she or her operator runs as a standing service and reaches with a bearer token (FR-62, FR-64). Her key need is unchanged and is the constraint the HTTP path must not violate: one API key, no host, no console ID, no TLS decisions. The HTTP path adds exactly one credential to that list — the inbound shared secret (ADR-04) — and nothing else. This is a served path, not a hosted service: the operator supplies their own UniFi key by environment variable, which is why the multi-tenant credential-collection blocker in ADR-01 does not apply (OQ-09, resolved).

### Secondary: Sam — Mobility operator

Manages UniFi Mobility for a workspace: cellular/data-plan-backed devices with an active cloud subscription. Is a workspace Admin. Needs `read:mobility` for inspection and `write:mobility` for the PUT operations that change device configuration. Is the persona most likely to hit a 403 caused by a *missing app scope on the key* rather than by a missing permission — a failure mode that is invisible unless the server names it.

**Key need:** an error path that says "your key lacks the `mobility` app scope; regenerate it at unifi.ui.com with that scope enabled" instead of "403 Forbidden". And an unambiguous signal that a Mobility PUT succeeded, given that Mobility PUTs return HTTP 204 with an empty body.

## 5. Functional Requirements

Priorities use MoSCoW: **Must Have**, **Should Have**, **Could Have**. Every FR carries at least one acceptance criterion phrased as a present-tense assertion or a "must" — no "should", "might", or "could" appears inside an acceptance criterion.

### 5.1 Spec ingestion and version management

| ID | Requirement | Priority | Acceptance Criteria |
|----|-------------|----------|---------------------|
| FR-01 | The four OpenAPI specifications are vendored into the repository as build inputs under a versioned directory (`specs/{service}/{version}/openapi.json`), fetched only from pinned-version URLs. The canonical sources are `https://developer.ui.com/site-manager/v1.0.0/openapi.json` (OpenAPI 3.0.3), `https://developer.ui.com/network/v10.4.57/openapi.json` (3.1.0), `https://developer.ui.com/protect/v7.1.87/openapi.json` (3.1.0), and `https://developer.ui.com/mobility/v1.0.0/openapi.json` (3.0.3). | Must Have | • The repository contains all four spec files at the pinned versions above, committed, with a recorded SHA-256 for each. • The server starts and serves a complete tool surface with no network access to `developer.ui.com` at runtime. • A grep of the repository for the literal string `/latest/openapi.json` returns zero matches in any code path that fetches a spec. |
| FR-02 | The spec-refresh routine bootstraps from `https://developer.ui.com/llms.txt`, which indexes all four services, their current versions, and every spec URL. It resolves current versions, fetches the pinned-version JSON for each, and — when any differs from the vendored copy — **prepares a pull request** on a local branch: it writes the new spec files and manifest, creates the branch, commits, and writes a PR body file containing the operation-level diff. It then prints the exact `git push` and `gh pr create` commands and stops. Opening the pull request is a deliberate human step; the routine never pushes and never calls the GitHub API. | Must Have | • Running the refresh command against a stubbed index that advertises a newer Network version produces a local branch containing the new spec file and an operation-level diff report, and does not modify the previously vendored version. • The refresh command never commits directly to the default branch. • The refresh command exits non-zero and changes nothing when the index cannot be retrieved. • The refresh command performs no network write: a run with the GitHub API and `git push` blocked completes successfully and still produces the branch, the commit, and the PR body file. • The command's final output names the `git push` and `gh pr create` invocations a human must run. |
| FR-03 | Every fetched spec response is validated as an OpenAPI document before it is written to disk: the body must parse as JSON and must contain an `openapi` version string and a non-empty `paths` object. A response that is HTML is rejected. | Must Have | • Given a fetch that returns HTTP 200 with an HTML document body (the failure mode produced by an unpinned `latest` URL), the routine fails with a message naming the URL and the reason, and writes no file. • Given a 200 response with a valid OpenAPI body, the file is written and its SHA-256 recorded. |
| FR-04 | Exactly one spec version per service is vendored and served at a time. The served version is **derived, not selected**: it is read from `specs/manifest.json` at startup and reported by server introspection (FR-55). There is no runtime configuration input that chooses among multiple vendored versions, and the server does not start with a silently substituted version because no substitution is possible. Changing the served version is a repository change reviewed through the refresh pull request (FR-02, FR-05), not an operator setting. Multi-version pinning for users on older controller firmware is **deferred** and tracked at OQ-16. | Could Have (downgraded from Must Have, 2026-08-01) | • The spec version reported for each service by server introspection exactly matches that service's `version` field in `specs/manifest.json`. • No `UNIFI_*` environment variable selects a spec version; a variable named to suggest one (for example `UNIFI_NETWORK_SPEC_VERSION`) is rejected at startup by the unknown-key validator (FR-54) with an error naming the variable. • The action registry contains exactly the operations present in the vendored spec named by the manifest, and no others. |
| FR-05 | Spec version bumps are reviewed, not absorbed. The refresh routine writes a **pull-request body file** containing a machine-generated diff listing added operations, removed operations, added/removed parameters, and added/removed response properties. A human opens the pull request from that file using the commands the routine prints (FR-02). | Must Have | • The generated PR body file enumerates every operation added and removed between the vendored and candidate spec. • A refresh producing zero operation-level differences still records the version change and the new SHA-256. • Merging a reviewed pull request is the only path by which the vendored spec files change on the default branch. • The PR body file is written to a known path and its location is named in the routine's output. |
| FR-06 | Because the Network and Protect specs declare **no `securitySchemes` and no `security` block at all**, the ingestion pipeline performs an explicit, documented post-processing auth-injection step for those two services, and asserts its own precondition. | Must Have | • The pipeline emits a warning naming Network and Protect when it detects an absent `securitySchemes`, and injects the API-key header requirement into the generated client for those services. • A test asserts that a request built for any Network or Protect operation carries the API key header. • If a future spec version *does* declare `securitySchemes`, the pipeline emits a notice that the injection step may now be redundant rather than silently double-applying it. |

### 5.2 Transport topology

| ID | Requirement | Priority | Acceptance Criteria |
|----|-------------|----------|---------------------|
| FR-07 | The server supports **cloud-direct** transport for Site Manager (`https://api.ui.com`) and Mobility (`https://api.ui.com/v1/mobility`) with no host configuration and standard public TLS verification. | Must Have | • With only an API key configured and no host, console ID, or TLS option set, a Site Manager list call and a Mobility list call both succeed. • Certificate verification is enabled for these hosts and cannot be disabled by the local-TLS opt-in of FR-09. |
| FR-08 | The server supports **local-direct** transport for Network at `https://{host}/proxy/network/integration` and Protect at `https://{host}/proxy/protect/integration`, with `{host}` user-supplied. | Must Have | • With a host configured, Network and Protect operations route to the local base URLs above. • The same tool names and the same argument shapes are used as in Connector mode; no tool name encodes the transport. |
| FR-09 | UniFi consoles ship self-signed TLS certificates. Local-direct mode therefore requires an **explicit, clearly-named opt-in** to relax verification, and/or a custom CA bundle path. Verification is enabled by default and defaulting to insecure is prohibited. | Must Have | • With a host configured and no TLS option set, a request to a self-signed console fails with a structured error that names the certificate problem and lists exactly two remedies: supply a CA bundle path, or set the named insecure opt-in. • The insecure opt-in is a single explicitly-named boolean setting (`UNIFI_LOCAL_TLS_INSECURE`) whose name contains the word `insecure`. • Setting the opt-in relaxes verification **only** for configured local console hosts and never for `api.ui.com`. • When the opt-in is active, the server emits a startup warning to stderr naming the affected hosts. |
| FR-10 | The server supports **Cloud Connector** transport, reaching on-premises Network and Protect through `https://api.ui.com/v1/connector/consoles/{consoleId}/proxy/network/integration/...` and `.../proxy/protect/integration/...`. The `/proxy/...` path form is used, per the `servers[]` entries in the Network and Protect specs, the path-parameter example, and `ai-gettingstarted.md`. | Must Have | • A Connector-mode request for a Network operation produces a URL containing `/v1/connector/consoles/{consoleId}/proxy/network/integration/`. • The same holds for Protect with `/proxy/protect/integration/`. • The path form used is asserted by a unit test with a recorded reference to the doc inconsistency (OQ-06). |
| FR-11 | Transport for Network and Protect is selected by **configuration**, not by tool choice. One tool surface serves both local-direct and Connector modes. | Must Have | • The set of tool names advertised at `tools/list` is byte-identical between a local-direct configuration and a Connector configuration with the same enabled APIs. • Switching a configuration value from local-direct to Connector changes only the resolved base URL, verified by a request-builder test. |
| FR-12 | Connector-specific documented constraints are enforced client-side: console firmware ≥ 5.0.3, **100 requests/minute per console**, a 25-second per-request timeout, and a 10 MB response body cap. Non-organization keys reach only the key owner's consoles; organization keys reach any console in the organization. | Must Have | • A per-console token bucket limits outbound Connector requests to 100/minute and a burst beyond that is queued or rejected with a structured rate-limit error carrying a retry hint, never silently dropped. • A Connector request exceeding 25 seconds is abandoned with a structured timeout error naming the console ID. • A response body exceeding 10 MB is rejected with a structured error instructing the caller to narrow the query, and is not buffered whole into the transcript path. • A Connector call against a console below firmware 5.0.3 surfaces the firmware requirement in the error text. |

### 5.3 Authentication and credentials

| ID | Requirement | Priority | Acceptance Criteria |
|----|-------------|----------|---------------------|
| FR-13 | All four APIs authenticate with an API key sent in the `X-API-Key` HTTP header. The server sets this header on every outbound request to every API, including Network and Protect where the spec declares no security scheme. | Must Have | • Every outbound request recorded by the request-builder test suite carries an `X-API-Key` header. • Header matching on inbound configuration is case-insensitive, consistent with HTTP header semantics. |
| FR-14 | The server supports **multiple credentials**: one cloud key (used for Site Manager, Mobility, and all Cloud Connector traffic) and zero or more local console keys, each bound to a configured console host. | Must Have | • With a cloud key and one local key configured, a Site Manager call uses the cloud key and a local-direct Network call to the bound host uses the local key, verified by request inspection. • A local-direct request to a host with no bound credential fails with a structured error naming the host and the configuration key required. • A Connector-mode Network call uses the cloud key, not a local key. |
| FR-15 | API keys are read from OS-keychain-backed storage, with an environment-variable path for headless and CI use. Keys are never written to plaintext files by the server. | Must Have | • A test asserts the server writes no file containing a configured key value anywhere under the user's config or state directories. • With a key present in the keychain and absent from the environment, the server authenticates successfully. • With the keychain unavailable, the server falls back to environment variables and logs, to stderr, that keychain storage is not in use. |
| FR-16 | Elicitation is never used to collect API keys or any other credential. | Must Have | • A grep of the source for elicitation request construction returns zero call sites whose prompt text references a key, token, secret, or password. |
| FR-17 | Site Manager keys are read-only today. The server treats Site Manager as a read-only API and states in its documentation that when Ubiquiti ships write endpoints, existing keys will not gain write access automatically — a manual key update will be required. | Must Have | • No Site Manager operation is exposed through the write execution tool. • The Site Manager section of the README states the manual-key-update requirement verbatim in substance. |

### 5.4 Tool surface

| ID | Requirement | Priority | Acceptance Criteria |
|----|-------------|----------|---------------------|
| FR-18 | The tool surface follows the **hybrid search + execute** pattern (see ADR-02): a small set of promoted read tools plus `unifi_search_actions` and two execution tools. The four specs total well over the 30-operation threshold at which one-tool-per-operation is prohibited. | Must Have | • `tools/list` with all four APIs enabled returns no more than 12 tools. • The total token cost of the advertised schemas is ≤ 3,000 tokens, asserted by a repo script (G-3). |
| FR-19 | `unifi_search_actions` accepts a natural-language intent string and optional service/method filters, and returns matching action IDs with their input schemas, HTTP method, owning service, and a read/write classification. **Action IDs are user-facing and stable.** Because callers save them in workflows and pass them verbatim to the execution tools, an ID must not change shape across a spec refresh that did not change the underlying operation. An ID is derived from the spec's `operationId` where the spec supplies one, and deterministically from HTTP method and path where it does not (FR-35 — the Protect spec supplies none). | Must Have | • Given the query "which access points are offline", the tool returns at least one Network device-listing action ID with its schema. • Given a query matching nothing, the tool returns an empty result set with a text hint naming the enabled services, not an error. • Every returned action ID is directly usable as input to an execution tool without transformation. • Results are bounded by a documented `limit` parameter with a default and a hard maximum. • Two builds from the same vendored spec SHAs produce byte-identical action IDs (NFR-22). • A spec refresh that changes no operation's method, path, or `operationId` changes no action ID, asserted by diffing the registry across the two vendored versions. • Where a refresh **does** change an action ID — including the case where a future spec version introduces an `operationId` for an operation whose ID was previously synthesised from method and path — the refresh diff (FR-05) lists every affected ID under a heading that names the change as breaking for saved workflows. The change is never absorbed silently. |
| FR-20 | `unifi_execute_action` executes a **read-only** action by ID. `unifi_execute_write_action` executes a **state-changing** action by ID. They are separate tools; neither accepts the other's action class. | Must Have | • `unifi_execute_action` given a write action ID returns a structured tool error stating the action is state-changing and naming the write tool, and performs no HTTP request. • `unifi_execute_write_action` given a read action ID returns a structured tool error naming the read tool. • `unifi_execute_write_action` is absent from `tools/list` under default configuration (G-6). |
| FR-21 | Exactly five operations are promoted to dedicated tools, chosen because they are the entry points from which every other question is reachable and are the operations a first-time user calls before anything else: `unifi_list_consoles`, `unifi_list_sites`, `unifi_list_devices`, `unifi_list_clients`, `unifi_list_cameras`. Rationale per tool is recorded in ADR-02. | Must Have | • All five tools appear in `tools/list` when their owning API is enabled and are absent when it is not. • Each is callable with zero required arguments and returns a useful first page. • Each carries `readOnlyHint: true`. • Each tool description names the sibling tools it is most likely to be confused with. |
| FR-22 | Tool exposure is filterable by configuration so a user who owns no Protect gear does not pay for Protect schemas. Each of the four APIs can be independently enabled or disabled. | Must Have | • With Protect disabled, `unifi_list_cameras` is absent from `tools/list`, `unifi_search_actions` returns no Protect actions, and the advertised schema token count drops measurably. • With a single API enabled, advertised schema token cost is ≤ 1,500 tokens. • Disabling an API the user has not configured credentials for is the default, not an opt-out. |

### 5.5 Normalized pagination and errors

| ID | Requirement | Priority | Acceptance Criteria |
|----|-------------|----------|---------------------|
| FR-23 | One **normalized pagination contract** spans all four APIs. | FR-26 | Rate limiting is handled uniformly. | `UNIFI_API_KEY_FILE` | *(unset)* | a readable path of at most 4 KiB | the cloud API key, otherwise `UNIFI_API_KEY` | FR-78, NFR-31 |
| `UNIFI_LOCAL_API_KEY_FILE` | *(unset)* | a readable path of at most 4 KiB | the **default** local console's API key, otherwise `UNIFI_LOCAL_API_KEY` | FR-78, NFR-31 |
| `UNIFI_LOCAL_API_KEY_<LABEL>_FILE` | *(unset)* | a readable path of at most 4 KiB | the API key for local console `<LABEL>`, otherwise `UNIFI_LOCAL_API_KEY_<LABEL>` | FR-78, NFR-31 |

**The `_FILE` suffix collides with the existing local-key family, and the collision is resolved here rather than discovered in production.** `src/config.ts:93` declares `const LOCAL_KEY_PREFIX = 'UNIFI_LOCAL_API_KEY_'`; `:377` admits **any** key matching that prefix as known, and `:201` binds `LOCAL_KEY_PREFIX + label` as console `label`'s key variable. So `UNIFI_LOCAL_API_KEY_FILE` is, today, a perfectly legal spelling of *"the API key for a local console labelled `FILE`"* — it passes the unknown-key check, and if no `UNIFI_LOCAL_HOST_FILE` is set it is then **silently ignored**, because `readLocalConsoles` derives its label set from the host variables. An operator who follows the documentation and puts their key in a file would get a server that starts cleanly and fails every local-direct call, with no error naming the variable. That is precisely the class of silent-ambiguity failure FR-78's own *"Ambiguity about which secret is live is not resolved silently"* criterion forbids.

**Disambiguation rule (normative).** Within the `UNIFI_LOCAL_API_KEY_` family the trailing `_FILE` suffix is **reserved**. A key of the form `UNIFI_LOCAL_API_KEY_<LABEL>_FILE` is file delivery for console `<LABEL>` and is never a key for a console named `<LABEL>_FILE`; `UNIFI_LOCAL_API_KEY_FILE` is file delivery for the **default** console and is never a key for a console named `FILE`. Consequently a local console whose label is `FILE`, or whose label ends in `_FILE`, is **unaddressable** and is refused at startup with an error naming `UNIFI_LOCAL_HOST_<LABEL>` and the reservation — a refusal, not a warning, because the alternative is a console whose key can be set but never read.

| FR-70 | The HTTP serving transport shuts down gracefully within a bounded, configurable deadline. On SIGTERM it: (1) marks itself not-ready (FR-69); (2) stops accepting new connections; (3) **stops admitting new outbound rate-limit acquisitions, fails queued waiters immediately with the existing structured `rate_limit` error, ABANDONS rather than awaits any in-progress rate-limit hop and any in-progress retry backoff, and makes no further retry attempt for any in-flight action, and FAILS RATHER THAN AWAITS ANY ACTION STILL RESOLVING CREDENTIALS** — the credential-resolution clause is added in Revision 5 (Architect S-STEP3); such an action is failed with the same structured error and for the same reason a queued waiter is failed, namely that it holds no rate-limit token and has issued no request. The clause was already carried by this requirement's own five-state derivation below, by RC-3's *"Third error"*, and by the `SIGTERM DURING CREDENTIAL RESOLUTION` acceptance criterion; it was missing only from this numbered step, so the step, the derivation and the criterion now agree; (4) **awaits the COMPLETION OF EACH IN-FLIGHT TOOL HANDLER — the handler's own promise, never the promise returned by `transport.handleRequest()`** — under the existing per-attempt deadline, so a client with an outstanding request receives a complete response. The distinction is load-bearing rather than pedantic (Revision 4): in JSON response mode `handleRequest`'s promise is settled **only** by `resolveJson`, and the JSON-mode `cleanup` at `webStandardStreamableHttp.js:583-585` deletes the map entry without ever calling it, so that promise is left **permanently pending** by `close()` (`sdk-facts.md` §A.5(ii)). A drain written to await the transport's request-handling promise therefore deadlocks the instant `enableJsonResponse` is ever turned on — a one-option change turning a graceful shutdown into a hang that only the hard stop escapes. SSE mode is the default and this requirement keeps it there; the drain must nonetheless hold its own set of in-flight handler promises, so that the mode cannot decide whether shutdown terminates; (5) **terminates every open session explicitly, in the order the SDK actually requires** — for each entry in **our own** session registry, first `transport.send()` a terminal JSON-RPC error frame, **because `transport.close()` writes no JSON-RPC frame at all** (it ends the response body and the client sees a truncated stream with no `result` and no `error`), then `await mcpServer.close()`, which chains `Protocol.close()` → `transport.close()` and, through the `onclose` wiring `connect()` installs, runs `Protocol._onclose()` — clearing every request-timeout timer and **aborting every in-flight request handler's `AbortController`**; (6) **calls `httpServer.closeAllConnections()`**, which is the **only** Node method that destroys a socket carrying an active SSE stream or a hung JSON-mode response — `close()` and `closeIdleConnections()` both use the "not sending a request or waiting for a response" predicate, and an open SSE response is by definition not idle; (7) **destroys every pooled outbound keep-alive agent** and exits 0. On deadline expiry it destroys remaining sockets and exits with a distinct non-zero status. **Steps (5) and (6) are re-specified in Revision 3.1 against the verified SDK and Node teardown record** (`01-idea/verification/sdk-facts.md`, Extension §A.1, §A.5, §B.5, §C.1). Three facts govern them. **First, `transport.close()` ends response BODIES, not sockets.** Its whole implementation (`webStandardStreamableHttp.js:771-787`) sets `_closed`, runs each stream's `cleanup()` — which clears the keep-alive interval and calls `streamController.close()` — clears three maps and fires `onclose`. `streamController.close()` ends the `ReadableStream`; the TCP socket becomes an *idle keep-alive* socket rather than a destroyed one, and **no JSON-RPC frame is written to the client**, which is why step (5) sends the terminal frame itself before closing. **Second, `close()` HANGS a request in JSON (non-SSE) mode.** With `enableJsonResponse: true`, `handleRequest` returns a promise settled only by `resolveJson`, and the JSON-mode `cleanup` (`:583-585`) deletes the map entry without ever calling it — so the promise stays **permanently pending** and the `ServerResponse` is never written. This server leaves `enableJsonResponse` at its default (SSE mode) and states so as a requirement; step (6) is nonetheless the only thing that would free such a connection if it were ever enabled. **Third, `closeAllConnections()` is not optional.** Node v20.20.2, verified empirically: with one idle socket and one mid-SSE socket, `close()` alone and `close()` + `closeIdleConnections()` both leave the SSE socket alive; only `close()` + `closeAllConnections()` destroys it, and the `close()` callback fires **only** in that case. Without step (6), `httpServer.close()`'s callback waits for every response to end **plus `keepAliveTimeout`** — about 6 seconds at the 5 000 ms default — before firing. **Step (7)'s agent destruction is not housekeeping — without it the process may never exit at all.** `src/http/client.ts:230-234` constructs `new Agent({ keepAlive: true, ... })` per TLS profile into a cache at `client.ts:84`, and `agent.destroy()` appears nowhere in `src/`; pooled sockets are `ref`'d handles, so "exits 0" is unreachable by natural event-loop drain and the process falls through to the hard stop on every clean shutdown. **Deadline derivation (re-derived twice; see RC-3).** The original 30-second figure was derived from the 25-second per-request deadline alone. The true worst case for one read action at repository defaults is three attempts, each paying a rate-limit hop and a full 25-second per-attempt timeout, separated by two honoured `Retry-After` sleeps capped at 30 seconds: `3 × (0.6 s + 25 s) + 2 × 30 s = 136.8 s`, and the rate limiter's FIFO chaining adds an unbounded queue term on top. No orchestrator grace period should be set from that number. **Step (3) is what makes the deadline derivable, and its residue is a MAXIMUM OVER STATES, NOT A SUM.** Rate-limit acquisition fully resolves at `client.ts:159` before `send()` is entered at `:163` and before the `AbortController` is created at `:269`, so an action is in exactly one of **five** states at any instant: **resolving credentials**, queued for a token, sleeping in a retry backoff, in flight under the 25-second per-attempt deadline, or between states for a negligible interval. #### 5.15.3 Trust boundary and threat model for the listener (normative)

This subsection is required by NFR-32. It exists so that a security review has an artefact to review against rather than a set of controls to infer. It is derived from ADR-05's boundary analysis and is maintained in step with it: the non-defence list below is asserted **equal** to ADR-05's *"What is deliberately not defended against"* list, and a member present in one and absent from the other is a defect (NFR-32, ADR-05 residual ADR-R7).

**Assets.** The operator's UniFi API keys, cloud and per-console. The inbound shared secret and its optional secondary. Session identifiers, which are bearer-equivalent because in stateful mode possession of one is sufficient to continue a session. And the ability to invoke actions against the operator's estate — which is the asset that does not look like a credential and is the one an attacker actually wants.

**Trust zones and the boundary between them.** On the **trusted** side: the process, its resolved configuration, the captured credential object, and the shared runtime that holds the action registry, the credential store and the outbound UniFi client. On the **untrusted** side: every inbound socket; every header, including `Host`, `Origin` and `Authorization`; every request body; every `Mcp-Session-Id` a caller presents; and the raw request target. The boundary is the inbound socket. Nothing arriving across it is trusted before the controls below have run, and the raw request target is discarded once the route is resolved rather than re-read later.

Binding a port is what creates this boundary. On stdio the caller population is whoever can already run the process; with a listener it becomes anyone who can reach the port, a set defined by network topology rather than by process ownership, which the operator does not choose explicitly and which is not observable from inside the process.

**Entry points across the boundary.** There are exactly three, and no fourth is added by this release: the **MCP endpoint** (`UNIFI_HTTP_PATH`, default `/mcp`), **`GET /healthz`**, and **`GET /readyz`**.

**Controls at each entry point, and the requirement that owns each.**

| All three, before any of them | The five startup refusals — the server refuses to start rather than binding into a configuration whose failure mode is a silently-exposed listener | FR-73 |
| All three, before any of them | Secret delivery by file and the environment scrub, so the credential is not left in `process.env` for the process lifetime | FR-78 |

**What is deliberately not defended against.** Stated so that the gaps are decisions rather than oversights, and so that no reader mistakes silence for coverage. This list is the same list as ADR-05's, by requirement.

- **A caller holding the shared secret is fully trusted.** There is no per-user identity and no per-request authorisation. Anyone with the secret can drive every enabled action, and authorisation granularity is by configuration and fixed for the lifetime of the process (Out of Scope #15, #19).
- **TLS is terminated upstream.** The listener speaks plain HTTP. An operator who exposes it beyond loopback without a proxy broadcasts the bearer secret in the clear, voiding every authentication control above. The startup warning on a non-loopback bind is the only mitigation the product ships (Out of Scope #14).
- **The authentication-failure throttle is bypassable by source rotation**, and its bounded table means a rotating attacker can evict the entries of genuinely throttled sources. It raises cost against a single source; it is not what protects the secret. The length floor and restricted network reach are (FR-81).
- **Behind a reverse proxy — the recommended shape, because it is the only way to get TLS — the throttle protects nothing.** Every request arrives from the proxy's address, so the source key collapses to one value for the entire caller population and per-source counting has nothing to count. The throttle is **inert** in that topology, and inert **by design rather than by accident**: a throttled source is still authenticated normally and is still served if its secret is valid, so a stranger who trips the shared key cannot lock out the legitimate client. No `X-Forwarded-*` header is consulted (Out of Scope #21).
- **The floor on the shared secret is a length floor, not an entropy floor.** Thirty-two identical characters satisfy it. Slot digests are unsalted SHA-256, so a digest recovered from a heap dump or a core file is offline-attackable at whatever entropy the operator's secret actually carries, not at 256 bits. The README's rotation guidance recommends a CSPRNG-generated value; the product does not measure one.
- **Any caller holding the secret — or one buggy client — can occupy every session slot and deny the operator's own client.** Refusing at the cap rather than evicting a live session is deliberate, but it has a mirror image: keeping every slot warm needs no malice, and a client that never sends `DELETE` and reconnects on every restart does it by accident. There is no per-source session cap in this round, no admin termination endpoint, and — since sessions are in-process — the operator's only remedy is to restart the process, which drops every session including the legitimate ones (FR-77).
- **The probe connection headroom raises the cost of probe starvation; it does not close it.** The reserved connections are reserved by *route*, and "probe" is a property of the request string rather than of the caller, so probe-shaped keep-alive traffic can occupy them. The per-source cap of one headroom connection defeats the single-source version completely; a distributed attacker with eight source keys is not defeated by it. The control that closes the attack is network reach (FR-76, NFR-29).
- **The `auth=none` mode on loopback is a real widening over stdio, not an equivalent.** On stdio the caller population is whoever can already run the process — a genuine property of process ownership, since such a caller can already read the environment, the configuration and the credential file. **A loopback socket carries no uid check of any kind.** Its caller population is every local uid that can open a TCP connection to `127.0.0.1`: every other account on a shared workstation, jump host or build machine, every container sharing the host network namespace, and every process of every user, including ones that could not spawn the server and could not read its secrets. It remains available because the operator must type the opt-out word and because it is refused outright off loopback, and the startup warning names the exposed population at the moment of the decision (FR-64, FR-73(e), NFR-23).
- **The composed unauthenticated surface is a reliable product fingerprint.** Two probe endpoints with fixed bodies identify the host as a UniFi MCP instance holding a live UniFi key, with zero credentials presented. That is the price of serving orchestrator probes unauthenticated, which is a deliberate trade (FR-67).
- **No brute-force alerting primitive ships.** Detection is the operator's, built by grepping the per-request log line. There is no metrics endpoint and no security-event stream (Out of Scope #20, NFR-24).
- **An attacker with read access to the host's process table or the Docker socket can recover the secret** before the environment scrub completes, and can read it from `docker inspect` output if it was supplied with `-e`. File delivery and `secretKeyRef` exist because of this (FR-78, NFR-31, OQ-15).
- **The uniform rejection is byte-identical, not time-identical.** No constant-time floor is specified across rejection classes; one would add latency to every rejection for a signal that is noisy across any real network (FR-81).

## 7. Out of Scope

Explicitly excluded from this release. Each entry names the reason, because "out of scope" without a reason gets relitigated.

1. **The legacy / undocumented UniFi controller API** (the `/api/s/{site}/...` cookie-session endpoints that community libraries wrap). It is unpublished, unversioned, and unsupported by Ubiquiti; building on it would put the server's stability at the mercy of an interface with no contract. This server covers the four *published developer* APIs only.
2. **UniFi Access, Talk, Drive, and Identity.** No published developer APIs exist for these products as of 2026-08-01. There is nothing to wrap. If Ubiquiti publishes specs at the same `https://developer.ui.com/{service}/{version}/openapi.json` pattern, the ingestion pipeline (FR-01–FR-05) extends to them without redesign — but that is a future release.
3. **Protect live video streaming, RTSP/RTSPS stream handling, WebRTC, two-way talkback, and continuous video export.** Streaming media is not representable in an MCP tool result and would require an out-of-band transport. Single-frame snapshot endpoints, where the vendored Protect spec exposes them, are in scope but return a reference rather than inline image bytes (see FR-37 and NFR-08).
4. **Write access to Site Manager.** Site Manager keys are read-only today. When Ubiquiti ships write endpoints, existing keys will not gain write access automatically, and a manual key update will be required (FR-17). Supporting a capability that does not exist yet is speculative work.
5. **Any user interface beyond the MCP protocol itself.** No web console, no TUI, no dashboard, no CLI beyond the maintainer-facing spec-refresh and coverage commands. The MCP client *is* the interface. This exclusion does not cover the operational probe endpoints `/healthz` and `/readyz` (FR-67, FR-68, FR-69), which are protocol infrastructure for an orchestrator rather than a user interface, carry bare status only, and are addressed by machines.
6. **A hosted, multi-tenant remote deployment.** See ADR-01 and ADR-05. UniFi publishes no OAuth, and the build skill states that Claude does not support user-pasted bearer tokens (`static_bearer`), so there is no supported mechanism for a hosted server to collect *each user's* UniFi key. That reasoning is unchanged and multi-tenant hosting stays out of scope. It does **not** extend to the single-tenant, self-hosted HTTP deployment added by ADR-05, where the operator supplies their own UniFi key by environment variable exactly as they do on stdio and there is no credential to collect from anyone. Revisit multi-tenant hosting if and when Ubiquiti publishes OAuth.
7. **A caching layer or local database of UniFi state.** Every read is a live read. A cache introduces staleness questions ("was that camera offline now or an hour ago?") that undermine the product's core value and would need its own invalidation design.
8. **A monitoring or alerting daemon.** The server answers questions when asked; it does not poll, watch, or notify. Long-running background polling is a different product with different rate-limit economics against the Connector's 100 req/min per console.
9. **Publishing YAML specifications.** Ubiquiti serves the specs as **JSON only**; no YAML variant is published anywhere on the portal. A local JSON→YAML conversion is possible but adds a second source of truth for zero functional gain, and is excluded (Assumption A-3).
10. **MCP `resources` and `prompts` primitives.** Version 1.0 ships `tools` only. Resources are a plausible future fit for vendored specs and console inventories, but adding a second primitive before the tool surface is proven splits the verification effort.
11. **Automatic absorption of vendor spec changes.** Spec bumps land as reviewed pull requests (FR-05). Auto-merging a firmware-versioned spec would let an operation appear in the tool surface with no human ever having read its description.
12. **Guaranteed compatibility with non-Claude MCP clients.** The server speaks standard MCP and will likely work elsewhere, but the payload ceilings, annotation semantics, and confirmation behaviour this PRD optimises for are Claude's. Other hosts are best-effort, untested, and unsupported in 1.0. The HTTP serving transport does not change this set. A deployment serving several clients from one instance inherits #12 unchanged: every client other than Claude is best-effort, untested and unsupported in 1.0, and the payload ceilings of NFR-08 remain calibrated for Claude.
13. **Bulk fleet orchestration primitives** (apply-to-all-consoles, scheduled sweeps, cross-console transactions). Marcus will want these. They are a v2 conversation that depends on resolving the Connector rate-limit economics first.

14. **In-process TLS termination.** The HTTP serving transport speaks plain HTTP and binds `127.0.0.1` by default. Certificate acquisition, renewal, and rotation are solved problems in the layer above — a reverse proxy, an ingress controller, or a service mesh — and reimplementing them inside the server would add a certificate lifecycle to a process whose entire security model is "one operator, one secret, one loopback bind." An operator exposing the listener beyond loopback is expected to terminate TLS in front of it, and the documentation says so.
15. **OAuth, OIDC, or any form of per-user identity.** The serving transport authenticates the *caller*, not a *user*: one shared secret, one operator, no identity model. UniFi itself publishes no OAuth, so there is no upstream identity to federate with even if one were wanted. This is the same constraint that keeps multi-tenant hosting out of scope (#6), viewed from the inbound side. See ADR-05.
16. **Multi-replica deployment of the HTTP serving transport.** Session state is in-process and is not shared or replicated, so a second replica cannot serve a session the first one initialised. More fundamentally, the shared-outbound-client design (NFR-15, NFR-26) makes fan-out actively counterproductive rather than merely unsupported: each replica carries its own token buckets, so N replicas multiply the outbound rate a UniFi console sees by N and produce exactly the self-inflicted 429s R-2 was opened against. Scale vertically or run one replica per console fleet.
17. **Stream resumability.** The transport is configured without an event store, so a client that disconnects mid-stream reconnects with a new session rather than replaying missed events. Resumability requires durable event storage with its own retention, ordering, and eviction design — a second stateful subsystem in a server that otherwise holds no state, for a failure mode a retry already covers.
18. **The deprecated HTTP+SSE transport.** Streamable-HTTP only. Supporting the older two-endpoint transport would double the inbound surface — and the security surface, since Host and Origin validation are owned in-repo (FR-65, FR-66) and would need to hold on both — to serve clients that the current SDK already marks deprecated.
19. **Per-request RBAC over the action surface.** Every caller presenting the shared secret gets the same tool surface. Authorisation granularity is by *configuration* — enabled services, write enablement per service, the HTTP write gate (FR-71) — and is fixed for the lifetime of the process, not evaluated per request. Per-request RBAC presupposes the per-user identity that #15 excludes; the two stand or fall together.
20. **Metrics, tracing, and an observability endpoint.** The server emits one structured log line per request (NFR-24) and nothing else: no `/metrics`, no counters endpoint, no tracing exporter. The probe endpoints deliberately carry bare status (FR-67), so session count, queue depth, rate-limit waits and 401/403 rates are not externally visible in 1.0 — an operator who needs them parses the log lines, which is why NFR-24's closed set now carries a bounded `reject_reason`, the effective write state and the client address. This is a real gap for the platform-team use case and is recorded as a decision rather than left to be discovered.
21. **Trusted-proxy support, and any use of `X-Forwarded-*` to identify the client.** *(Added in Revision 6; architecture residual AR-5, ADR-05 residual ADR-R6.)* Behind a reverse proxy — the recommended shape, because it is the only way to get TLS — every request arrives from the proxy's address, so the FR-81 throttle's source key collapses to one value for the whole caller population and per-source counting has nothing to count. **The throttle is therefore inert in that topology, and it is inert by design rather than by accident:** a throttled source is still authenticated normally and is still served if its secret is valid (FR-81), so a stranger cannot lock out the legitimate client. Restoring per-client counting means trusting a caller-supplied header, which is a security decision an order of magnitude larger than the control it would restore — the throttle raises brute-force cost and is explicitly **not** what protects the secret; the 32-character floor and restricted network reach are. A `UNIFI_HTTP_TRUSTED_PROXY` row would also have to be added to the family FR-63 closes, which is a requirement change rather than a configuration one. Excluded for 1.0 and recorded here rather than left silent, because silence next to a shipped throttle reads as "the throttle works behind a proxy", and it does not.
22. **Credential delivery by command-line argument.** *(Added in Revision 7; owner decision on OQ-19.)* No secret this server holds — not the inbound shared secret, not any UniFi API key — may be supplied on the command line, and the capability is excluded rather than merely unimplemented. It was proposed, considered and rejected on the exposure argument, not on effort: `argv` is readable in `ps`, in `/proc/<pid>/cmdline` by any process running as the same uid, and in `docker inspect` by anyone with access to the Docker socket, so a command-line key is strictly more exposed than the environment variable it would sit beside — and the environment variable is itself the exposure `*_FILE` delivery and the FR-78 scrub exist to reduce. It would add a third delivery path with worse properties than both existing ones and no case the `*_FILE` path does not already serve. The supported deliveries are, in resolution order: the `*_FILE` variables of §5.15.1 and §5.15.1b, the environment, and — on shapes that carry it — the OS keychain, bounded by FR-82. FR-78 asserts the exclusion, so re-proposing this fails a test rather than a review.

## 11. Architecture Decisions

These five decisions are **DECIDED**, not proposed. ADR-01 through ADR-04 were made so that `mcp-server-dev:build-mcp-server` could skip its discovery phase; ADR-05 was made afterwards, once the server existed and a deployment shape the original four did not anticipate was required. ADR-05 **amends** ADR-01 rather than superseding it, and the amendment is narrow: ADR-01 rejected a remote deployment on two independent grounds, and only one of them — the multi-tenant credential-collection blocker — is retired by the single-tenant reframing. **The local-direct LAN routing ground is not retired.** It becomes an operator obligation: an HTTP-served process must be deployed on a network with a route to the consoles it is configured to reach, and stdio remains the default transport (FR-79). ADR-01's Option D also warned that two deployment models means two security models, two configuration stories and two things to get wrong; that con was not a multi-tenant argument and it has come true — this round adds a second security model (bearer secret, `Host` validation, `Origin` rejection, five startup refusals) and a second configuration story (§5.15.1). It is accepted knowingly, with the cost paid down by making the second model refuse to start rather than start unsafely. Residual uncertainty has been pushed into Section 10 (Open Questions) and does not reopen these decisions.

### ADR-01 — Deployment model: **local server (stdio default), distributed as MCPB and as a container image** *(amended by ADR-05)*

**Date:** 2026-08-01 · **Decision Maker:** Repo maintainer · **Status:** Decided; amended 2026-08-01 by ADR-05 (serving transport selected by configuration; stdio remains the default)

#### Context

The `mcp-server-dev:build-mcp-server` skill's default is emphatic: *"Remote streamable-HTTP… This is the recommended path for anything wrapping a cloud API. Choose this unless the server must touch the user's local machine."* MCPB is *"when the server must run on the user's machine — it reads local files, drives a desktop app, talks to localhost services, or needs OS-level access."* Local stdio is *"not recommended for distribution… Fine for personal tools and prototypes."*

UniFi splits down the middle of that rule, which is why this cannot be inherited as a default:

- **Site Manager and Mobility** are cloud APIs on `api.ui.com`. Textbook remote HTTP.
- **Network and Protect via Cloud Connector** are reachable from anywhere through `api.ui.com`. Remote HTTP works.
- **Network and Protect in local-direct mode are on the user's LAN at a private address.** A remote HTTP server cannot reach `192.168.x.x`. This is not a preference; it is routing.

Auth compounds it. UniFi uses a long-lived, user-supplied API key created at `unifi.ui.com` or on the local console, shown once. The build skill states Claude does not support *"user-pasted bearer tokens (`static_bearer`)"*, and Ubiquiti publishes no OAuth. A hosted multi-tenant remote server would need each user's UniFi key with **no supported mechanism to collect it**. That is not a difficulty to engineer around; it is a missing primitive.

#### Options Considered

**Option A: Remote streamable-HTTP covering cloud + Connector only; local-direct declared out of scope**
- Pros: The skill's recommended default. No distribution problem — users add a URL. Centralised updates. Serves Priya and most of Marcus.
- Cons: **Abandons Dana entirely**, the primary persona. Local-direct is not a niche: it is how every single-console owner with the controller on their own LAN actually operates, and it is the only mode with no rate limit and no 25-second timeout. And the auth primitive does not exist — a hosted deployment has no supported way to collect a user's UniFi key. This option is blocked on two independent grounds, either of which alone would sink it.

**Option B: Local stdio only, no packaging**
- Pros: Simplest. Reaches everything — LAN and cloud alike. No auth-collection problem: the key is in the user's own keychain. Zero infrastructure.
- Cons: The skill calls plain stdio *"not recommended for distribution."* Requires the user to have a runtime installed and to hand-edit MCP configuration. Fine for the maintainer, poor for Dana.

**Option C: Local server distributed as MCPB** *(chosen)*
- Pros: Reaches the LAN, which is the hard requirement. Bundles the runtime, so Dana installs one file. MCPB manifests support configuration fields marked `sensitive: true`, which is exactly the credential surface needed (NFR-13). Keychain access is available because the process runs as the user. Serves all four personas from one artifact.
- Cons: Distribution work — bundling, and possibly code signing per platform (OQ-08). Updates ship as new bundles rather than server-side. Does not serve a browser-only user with no machine to install on.

**Option D: Both shapes from one codebase, transport chosen by configuration**
- Pros: Theoretically serves everyone. The core (spec ingestion, action registry, normalization, safety gating) is genuinely transport-agnostic.
- Cons: **Doubles the verification surface at exactly the moment there is no test scaffolding** (R-7), for a remote half that still cannot collect credentials (the Option A blocker, unchanged). Two deployment models means two security models, two configuration stories, two sets of documentation, and two things to get wrong — before either is proven.

#### Decision

**Ship a local server on stdio transport, distributed as an MCPB bundle.** Plain local stdio via `claude mcp add` is the development and early-adopter path (M1–M4); MCPB packaging is the distribution format at M5.

The answer is "local, for now," and this document says so plainly rather than pretending remote was chosen. The local-direct requirement is a routing fact that no amount of architecture removes, and the credential-collection gap makes hosted remote unavailable rather than merely inadvisable. The build skill's own MCPB criterion — *"talks to localhost services"* — is satisfied in substance: the server talks to a service on the user's LAN that no external host can reach.

**Option D was rejected for v1 as it was framed here — both shapes, including a hosted multi-tenant remote — and is now *partially adopted*, by ADR-05.** What was rejected and stays rejected is the hosted, multi-tenant remote half: it still cannot collect each user's UniFi key, so it still buys nothing that works (Out of Scope #6). What is adopted is the narrower shape this option did not distinguish at the time — a **single-tenant, self-hosted** serving transport selected by configuration, where the operator supplies their own key by environment variable and no credential-collection mechanism is required at all. **The separability this option's rejection was conditioned on is now a requirement placed on the implementation, not an observation about it:** adding the HTTP entrypoint must change `src/index.ts`, add `src/serve/`, and extend `src/config.ts` (the recognised-key list, without which every new variable is fatal) and `package.json` (the SDK floor, NFR-28) — and must not change `src/tools/*`, `src/registry/*`, `src/safety/*` or `src/network/*`. **Two files under `src/http/` are named exceptions, permitted and bounded** (amended in Revision 3): `src/http/client.ts` and `src/http/ratelimit.ts` may change **only** to add lifecycle affordances — a way to stop the limiter admitting acquisitions and to abandon an in-progress wait, a way to abandon an in-progress retry backoff, and a way to release the pooled keep-alive agents. **No behavioural change to request construction, to retry policy, or to rate-limit arithmetic is permitted.** This exception is not a concession, it is a fact about the code: `RateLimiter` (`src/http/ratelimit.ts:41`) exposes no `close`, `dispose`, `drain` or `abort` and accepts no `AbortSignal`; its `acquire()` takes only a bucket key; its tail chain swallows both settlement paths (`:79-82`), so a wrapper outside the class cannot stop it; `UnifiClient` (`src/http/client.ts:80`) exposes no `close()`; and `agent.destroy()` is called nowhere in `src/`. A graceful drain that terminates within a derivable deadline (FR-70, RC-3) is **impossible** without editing both files, so a claim that they do not change is a claim the implementation must falsify. This spec deliberately does **not** design the affordances — their shape, naming and error semantics are the Architect's decision at ADR-05 — it requires only that they exist and that their blast radius is bounded as stated. That claim is checkable: a CI diff-scope check asserts it on the transport change, treating any hunk in `src/http/client.ts` or `src/http/ratelimit.ts` that touches URL assembly, header construction, attempt counting, backoff computation, token accounting or refill arithmetic as a failure (FR-62, FR-70, FR-74). It is stated here as an obligation because at the time of writing `src/serve/` does not exist, and a decision record must not assert as history the outcome of code that has not been written. **The stated cost of Option D — doubling the verification surface at a moment with no test scaffolding (R-7) — is accepted, not retired.** The transport ships alongside a harness that is scheduled in the same round and is outstanding at the time of writing (§9, M2; §14 item 9; FR-75), and the risk of the doubled verification surface is live until that harness lands. Option D's other con — two deployment models means two security models, two configuration stories and two things to get wrong — was never a multi-tenant argument and has come true; it is accepted knowingly and paid down by requiring the second model to refuse to start rather than start unsafely (FR-73). See ADR-05.

#### Implications

- Local-direct, cloud-direct, and Connector transports are all in scope from one artifact (FR-07–FR-11).
- Credentials live in the OS keychain with an environment-variable fallback (FR-15, NFR-13) **in the desktop and MCPB shape**, where it is a benefit of the choice rather than a workaround. **The benefit does not transfer to the container shape.** The image installs with optional dependencies omitted, so `keytar` is deliberately absent and the fallback is the only path: credentials arrive by environment variable or by file (FR-78), and the residual exposure is the one OQ-15 tracks. NFR-13 is scoped accordingly.
- Distribution cost is real and owned: MCPB bundling and possible signing (OQ-08, R-12). It is scheduled at M5 and cannot block M1–M4.
- Ruled out, and still ruled out after ADR-05: any **hosted, multi-tenant** deployment (Out of Scope #6) — the credential-collection blocker is unchanged; and any browser-only usage. **No longer ruled out:** a single-tenant, self-hosted deployment reached over streamable-HTTP, added by ADR-05, where the operator supplies their own UniFi key exactly as on stdio.
- Distribution has two vehicles, not one. A multi-arch container image published to `ghcr.io/p47phoenix/unifi-mcp` shipped ahead of MCPB and is the vehicle the platform-team use case actually consumes; MCPB remains the desktop-install path (M5). The container serves both shapes: spawned per session over stdio (`docker run -i --rm ...`, unchanged), or run as a standing service under `UNIFI_MCP_TRANSPORT=http` (ADR-05, M7). Neither vehicle changes the credential story — keys arrive by environment variable in the container, where the keychain path is skipped and `keytar` is deliberately excluded from the image.
- The skill's **MCPB upgrade path** is the stated route from prototype to distribution, and it is on the timeline rather than aspirational.
- If Ubiquiti publishes OAuth, OQ-09 reopens this decision with materially better inputs.

#### Review Date

Reopened 2026-08-01 under a trigger this clause did not anticipate: an operator requested a deployment shape the original decision did not contemplate — a single-tenant, self-hosted service — and the reasoning that excluded it turned out to conflate two shapes (OQ-09). The amendment is ADR-05. The original triggers stand for the parts still rejected: reopen the hosted multi-tenant question when either (a) Ubiquiti publishes an OAuth flow for developer API access, or (b) post-1.0 usage shows cloud-only users are the dominant segment — whichever comes first.

### ADR-02 — Tool pattern: **hybrid — 5 promoted read tools + search/execute**

**Date:** 2026-08-01 · **Decision Maker:** Repo maintainer · **Status:** Decided

#### Context

The build skill's thresholds: 1–15 operations → one tool per action ("sweet spot"); 15–30 → "still workable, audit for near-duplicates"; **30+ → "switch to search + execute"**. It also offers a hybrid: *"Promote the 3–5 most-used actions to dedicated tools, keep the long tail behind search/execute."*

The rationale is context economics, not a protocol limit: *"Every tool schema is tokens Claude spends every turn. Thirty tools with rich schemas can eat 3–5k tokens before the conversation even starts."* And: *"listing every operation as a tool floods the context window and degrades model performance."*

Four UniFi specs total **168 operations** — site-manager 14, network 73, protect 73, mobility 8 (counted from the vendored specs and committed in `specs/manifest.json`; OQ-12, resolved). That is not near the 30 threshold — it is 5.6 times past it.

#### Options Considered

**Option A: One tool per operation**
- Pros: Every operation directly discoverable in `tools/list`. No search round-trip. Richest static schemas.
- Cons: 168 tools. Well over 25,000 tokens of schema before a single message is exchanged, against a Claude Code payload budget of roughly 25,000 tokens *total*. This does not degrade performance; it consumes the context window outright. Not viable at any size of estate.

**Option B: Pure search + execute**
- Pros: Minimal, fixed context cost regardless of how many operations exist — the pattern the skill prescribes above 30. Scales to future APIs (Access, Talk) with no schema growth.
- Cons: Every interaction pays a search round-trip, including the ones every user makes first. "List my sites" becoming two tool calls is a poor first impression and a measurable latency cost on the most common path.

**Option C: Hybrid — promote the highest-traffic reads, long tail behind search/execute** *(chosen)*
- Pros: The skill's own recommended refinement. Common questions answer in one call; the long tail stays free. Promoted tools double as the discovery entry points a new user needs before they know anything about their own estate.
- Cons: Two mental models. Requires defending which operations get promoted, and re-defending it as usage data arrives.

#### Decision

**Hybrid.** Exactly **five** operations are promoted to dedicated tools, plus `unifi_search_actions`, plus **two** execution tools (`unifi_execute_action` for reads, `unifi_execute_write_action` for writes — separate because NFR-01 requires it and directory review auto-rejects a combined tool).

The five promotions, each argued rather than assumed:

1. **`unifi_list_consoles`** (Site Manager). Promoted because it is the **discovery primitive for the entire Connector transport**. Marcus cannot construct a single Connector request without a `consoleId`, and there is no other way to obtain one (FR-53). A user who must first search for the tool that tells them what their consoles are called has been failed at step zero. It also returns firmware versions, which determine Connector eligibility (≥ 5.0.3) — so one call answers both "what can I address" and "what can I reach".
2. **`unifi_list_sites`** (Site Manager). Promoted because a site identifier is an **argument to most Network operations**. It sits on the critical path of nearly every Network question, so making it a search round-trip taxes the majority of interactions. It is also the natural first call for a cloud-only user (Priya) who has nothing else configured.
3. **`unifi_list_devices`** (Network). Promoted on **traffic**: "what's on my network / what's offline / what firmware is my AP on" is the single most common class of question this product exists to answer. It is also the entry point for device-scoped follow-ups, so it appears early in most multi-turn sequences.
4. **`unifi_list_clients`** (Network). Promoted on **traffic and distinctness**. It is the second most common question class and — critically — it is the tool most easily confused with `unifi_list_devices`. Promoting both, with descriptions that name each other as near-siblings (NFR-03), disambiguates them structurally. Left in the search tail, a search for "what's connected" would surface both and the disambiguation burden would fall on the model every time.
5. **`unifi_list_cameras`** (Protect). Promoted because it is the **only Protect entry point** and because Protect is the API most in need of a shaped tool: it has no pagination at all and returns full arrays (FR-36, FR-37). A generic `execute_action` over a Protect list endpoint has nowhere natural to put slicing and projection defaults. Promoting it makes the bounded, projected shape the default rather than an option a caller has to know to request.

Rejected for promotion despite being plausible: Mobility device listing (Sam is a secondary persona and the smallest spec; the extra schema cost is not repaid by traffic), and any write operation (writes are absent by default, so promoting one would advertise a tool that usually is not there).

**Tool exposure is filterable by configuration.** Each API is independently enableable (FR-22). A user who owns no Protect gear does not pay for Protect schemas — and given that the entire justification for this pattern is token cost, charging a Protect-free user for Protect schemas would contradict the decision.

#### Implications

- `tools/list` returns at most 12 tools with all four APIs enabled (FR-18), against a budget of 3,000 tokens (G-3, NFR-18).
- `unifi_search_actions` must return directly-usable action IDs and their schemas (FR-19) — if the search result needs interpretation, the pattern fails.
- Ruled out: adding a sixth promoted tool without a corresponding token-budget measurement. Promotions are a budgeted resource, not a convenience.
- The action registry becomes the central data structure: it carries every operation's ID, schema, service, read/write class, scope requirements, and rate-limit bucket.
- Adding a fifth API later costs approximately zero schema tokens for its long tail.

#### Review Date

Reconsider the promotion set after 90 days of real usage (M6), on evidence of which actions are actually executed most.

### ADR-03 — Framework: **official TypeScript SDK (`@modelcontextprotocol/sdk`)**

**Date:** 2026-08-01 · **Decision Maker:** Repo maintainer · **Status:** Decided

#### Context

The build skill recommends exactly two frameworks and has a default: **the official TypeScript SDK (`@modelcontextprotocol/sdk`) is the default choice** — *"best spec coverage, first to get new features."* **FastMCP 3.x** (jlowin's PyPI package, not the frozen FastMCP 1.0 inside the official `mcp` SDK) is the Python alternative — *"user prefers Python, or wrapping a Python library."* It adds: *"If the user already has a language/stack in mind, go with it — both produce identical wire protocol."*

The repository is greenfield with one commit and no stated language preference, so the tiebreaker must come from the workload: an HTTP client, OpenAPI schema handling across 3.0.3 and 3.1.0 documents, and — because ADR-01 chose MCPB — runtime bundling.

#### Options Considered

**Option A: Official TypeScript SDK** *(chosen)*
- Pros: The skill's stated default, with best spec coverage and first access to new MCP features — which matters for a server leaning on `outputSchema`/`structuredContent` (NFR-09) and on annotation semantics (NFR-02). **MCPB bundling is a Node story first**: the `mcpb` tooling and Node runtime bundling are the well-trodden path, and ADR-01 makes bundling a shipping requirement, not a nice-to-have. `keytar` is the credential-storage module the skill names for local servers (NFR-13). OpenAPI 3.1 is JSON Schema 2020-12, which lands natively in the TypeScript/zod/ajv ecosystem with no impedance mismatch. Generating TypeScript types from the vendored specs gives compile-time checking over an action registry built from four large documents. `fetch`/`undici` covers the HTTP needs including per-host TLS configuration for the self-signed-certificate case (FR-09).
- Cons: OpenAPI-to-client codegen in TypeScript is a crowded field with no single obvious winner, so tool selection needs a small spike. Native modules (`keytar`) complicate cross-platform bundling (OQ-08) — though this cost exists in Python too.

**Option B: FastMCP 3.x (Python)**
- Pros: Ergonomic decorators; excellent OpenAPI tooling; `keyring` is a mature credential library; strong for anyone more fluent in Python.
- Cons: The skill's stated triggers for choosing it — *"user prefers Python, or wrapping a Python library"* — are **both absent here**. There is no stated preference and no Python library being wrapped; UniFi is reached over plain HTTPS. Bundling a Python runtime into an MCPB for three platforms is heavier and less trodden than the Node path, and ADR-01 makes that cost load-bearing. Choosing it would mean overriding the skill's default with no reason drawn from the workload.

**Option C: a third language (Go, Rust)**
- Pros: Single static binary would genuinely simplify distribution, which is the main cost of ADR-01.
- Cons: The skill recommends exactly two frameworks, and a third would need an argument that **both** recommended options fail. Neither fails: TypeScript covers the workload cleanly. Going outside the recommendation costs first-class MCP SDK support, the MCPB tooling path, and the skill's own scaffolding — to save packaging effort that MCPB already solves. Not justified.

#### Decision

**Official TypeScript SDK (`@modelcontextprotocol/sdk`) on Node.**

The decisive factor is not language preference — there is none to honour — but that the MCPB requirement from ADR-01 and the schema-handling workload both point the same way, and they point at the skill's default. Choosing the default when the workload independently agrees with it is the cheapest correct decision available.

#### Implications

- Credential storage uses `keytar` (NFR-13); the environment-variable fallback covers headless Linux where no keychain daemon exists (NFR-20, OQ-15).
- Spec ingestion produces TypeScript types and a typed action registry from the vendored JSON specs, deterministically (NFR-22).
- MCPB bundling follows the Node path at M5; the native `keytar` dependency is the specific risk to spike (OQ-08).
- Ruled out: Python and any third language for v1. Reopening requires a workload fact that changes, not a preference.
- All diagnostics go to stderr, because stdio transport owns stdout (NFR-19).

#### Review Date

Not scheduled. Revisit only if MCPB Node bundling proves unworkable on a required platform (OQ-08), in which case distribution — not framework — is what changes.

### ADR-04 — Auth: **user-supplied API keys in the OS keychain, multi-credential by target, never in the transcript**

**Date:** 2026-08-01 · **Decision Maker:** Repo maintainer · **Status:** Decided; extended 2026-08-01 to cover the inbound shared secret introduced by ADR-05

#### Context

All four UniFi APIs authenticate with a long-lived API key in an HTTP header (`X-API-Key`; casing varies across Ubiquiti's own docs, and HTTP headers are case-insensitive — OQ-05). Keys are created at `https://unifi.ui.com` → Settings → API Keys for cloud use, or on the local console under Integrations, and are **shown once at creation**.

Complications the design must absorb:

- **Network and Protect specs declare no `securitySchemes` and no `security` block at all.** A generator that trusts the spec emits unauthenticated clients (FR-06, R-8).
- **Mobility needs a `mobility` app scope** on the key (403 without it), plus `read:mobility` for GETs and `write:mobility` for PUTs; the caller needs workspace Admin, and writes need an active cloud subscription on the target device.
- **Site Manager keys are read-only today**, and when write endpoints ship, existing keys will not gain write access automatically.
- **A user may legitimately hold two or more keys**: a cloud key from `unifi.ui.com` (serving Site Manager, Mobility, and all Connector traffic) and one or more local console keys created on each console's Integrations page.

Skill constraints that bind: for local/MCPB servers, tokens belong in the **OS keychain** (`keytar`/`keyring`) — *"Never plaintext on disk"*; MCPB manifests mark such fields `sensitive: true`; *"Tool results flow into the chat transcript. Anything you return, the user (and any log export) can see. Redact before returning."* And elicitation **must not** be used to collect API keys.

#### Options Considered

**Option A: Single key, one credential for everything**
- Pros: Simplest possible configuration and documentation.
- Cons: Factually wrong. A cloud key does not authenticate to a local console's integration endpoint, and a local console key does not authenticate to `api.ui.com`. Dana with a local console and Priya with a cloud key are not the same configuration, and a user who is both is not exotic. This option cannot express local-direct plus cloud simultaneously.

**Option B: Keychain-first, multi-credential, resolved by target** *(chosen)*
- Pros: Models reality: one cloud key plus zero or more host-bound local keys, resolved per request by which target the operation routes to (FR-14). Keychain storage satisfies the never-plaintext constraint. Environment-variable fallback keeps CI and headless Linux working. MCPB `sensitive: true` handles the install-time input path without elicitation.
- Cons: More configuration surface, and a harder error-message job — "which key was even used?" must be answerable without printing any key.

**Option C: Plaintext config file**
- Pros: Trivially portable, easy to inspect and version.
- Cons: Directly violates *"Never plaintext on disk."* Rejected outright.

**Option D: Prompt the user for the key through elicitation**
- Pros: Smooth in-chat onboarding.
- Cons: Explicitly prohibited — elicitation must not be used to collect API keys. Rejected outright.

#### Decision

**Option B.** Specifically:

- **How the key reaches the server:** at install/configure time, via MCPB manifest configuration fields marked `sensitive: true`, or via environment variables for development, CI, and headless use. Never via elicitation. Never via a tool argument.
- **Where it rests:** the OS keychain via `keytar`, with an environment-variable fallback when no keychain is available; a stderr notice states which path is in use (FR-15). The server writes no plaintext credential file, ever (NFR-13).
- **Multiple keys:** one **cloud key** used for Site Manager, Mobility, and all Cloud Connector traffic; zero or more **local console keys**, each bound to a configured console host. Credential selection is derived from the resolved request target, never from a caller-supplied argument (FR-14). A local-direct request to a host with no bound credential fails with a structured error naming the host and the exact configuration key required — and naming no key material.
- **Scopes as data:** Mobility scope requirements (`mobility` app scope, `read:mobility`, `write:mobility`) are recorded in action metadata and surfaced in descriptions and in the 403 recovery hint (FR-39, FR-40). Site Manager's read-only status is likewise data, not a hard-coded branch, so the eventual arrival of write endpoints is a spec change rather than a code change (FR-17).
- **Auth injection:** because the Network and Protect specs declare no security scheme, the ingestion pipeline injects the header requirement for those services in a documented post-generation step that asserts its own precondition (FR-06).
- **Never in the transcript:** key values never appear in tool results, `structuredContent`, error messages, or logs. Enforced by an automated scan for a planted sentinel value across every output channel (NFR-12).
- **A second credential class — the inbound shared secret.** The HTTP serving transport (ADR-05) requires a bearer secret from callers. It is **not a UniFi credential**: it authenticates nothing to `api.ui.com`, grants no access to a console, and cannot be replayed against Ubiquiti. It is nonetheless governed by every rule above, because **its compromise is equivalent to compromise of the UniFi key it stands in front of**: whoever presents it drives a process that already holds the operator's key, so the blast radius is identical even though the credential is not. Concretely: it is resolved **once at startup, from a file first (`*_FILE`) and from the environment second** (FR-78) — **not** through the keychain, which does not exist in the container shape at all, since the image installs with optional dependencies omitted and `keytar` is deliberately excluded; where a keychain *is* available (the desktop/MCPB shape) the credential store may serve it, but no requirement depends on that and the container path is the documented default. Resolving it does not require a UniFi-shaped lookup: the existing credential store is keyed on service and transport mode for UniFi routing, so the inbound secret is resolved by its own path rather than by inventing a service identifier for it. Once resolved, its environment variable is deleted from `process.env` (FR-78, NFR-31), because the environment is not a private channel — `/proc/self/environ`, `docker inspect`, `kubectl describe pod` and every child process see it. It never lands on `ServerConfig` and is never part of any introspection output (FR-55); it is compared by hashing both sides with SHA-256 and then `timingSafeEqual`, so the comparison can neither throw on a length mismatch nor branch on a partial match; it has a minimum length and its failures are throttled (FR-81); and it never appears in a log line, an error message, an HTTP response body, or a response header (NFR-12, NFR-24). A secondary secret may be configured concurrently so that rotation is a rolling operation rather than an outage (FR-64). `Mcp-Session-Id` values are treated as bearer-equivalent for the same reason and under the same rules, and are generated from a CSPRNG with a stated minimum entropy (FR-77). The only way to run without a secret is for the operator to set the authentication mode to the literal word `none`, which is legal only on a loopback bind (FR-64, FR-73(e), NFR-23).

#### Implications

- Configuration validation must catch enabled-API-without-credential at startup and name it (FR-54), rather than surfacing it as a confusing 401 at first call.
- Error messages must be diagnosable without revealing key material: they name the *target* and the *configuration key*, never the value.
- Server introspection reports effective configuration with secrets redacted, verified by sentinel test (FR-55).
- Ruled out: any credential path through elicitation, any plaintext credential file, any tool argument that accepts a key, and — for the inbound shared secret — any default value, any generated-and-printed value, and any configuration in which a listener binds without either a secret or the operator having typed the literal opt-out word (NFR-23).
- Headless environments accept environment-variable storage as a documented trade-off rather than a silent one (OQ-15).

#### Review Date

Extended 2026-08-01 under a trigger this clause did not anticipate: a second credential class — the inbound shared secret of the HTTP serving transport (ADR-05) — entered the product without any change in what Ubiquiti publishes. The original trigger stands for the UniFi-facing half: reopen if Ubiquiti publishes OAuth, which would change both this decision and ADR-01.

### ADR-05 — Serving transport: **selected by configuration; stdio default, single-tenant self-hosted streamable-HTTP available** *(amends ADR-01)*

**Date:** 2026-08-02 · **Decision Maker:** Repo maintainer · **Status:** Decided; **amends ADR-01, does not supersede it**

#### Context

ADR-01 chose a local stdio server distributed as MCPB, and rejected a remote deployment. Read its Option A rejection and its Option D con together and it rejected it on **three independent grounds**, not two: the credential-collection blocker, local-direct LAN routing, and a doubled verification surface at a moment with no test scaffolding. This ADR exists because the first was re-examined and found not to apply to the shape asked for. The second survives. The third has changed materially and is disposed of on its merits below rather than passed over.

**Ground one — the credential-collection blocker.** ADR-01 §Context: *"A hosted multi-tenant remote server would need each user's UniFi key with **no supported mechanism to collect it**. That is not a difficulty to engineer around; it is a missing primitive."* That reasoning is correct and it still holds — **for a hosted, multi-tenant server**. It does not hold for the shape asked for here. In a **single-tenant, self-hosted** deployment there is no "each user": there is one operator, running the process on their own infrastructure, supplying their own key by environment variable or by file, exactly as they already do on stdio. Nothing has to be collected, because nothing belongs to anyone else. The container image this repository already publishes (`ghcr.io/p47phoenix/unifi-mcp`, shipped at `b853a5e`) is that deployment today, minus a listener.

OQ-09 asked whether that shape was worth shipping and answered itself in the negative by accident. Its wording said remote HTTP was excluded *"solely because the auth mechanism does not exist."* **The word "solely" is the error.** It asserted one blocker where there were two, and it attached that one blocker to a deployment shape it does not apply to. A reader — including every reader of this PRD for a full round — took the question as closed. It was open. The word is corrected in OQ-09's own text by edit E-30, because correcting the answer without correcting the sentence that hid it leaves the same trap for the next question.

**Ground two — local-direct LAN routing. This ground is not retired, and this ADR does not retire it.** ADR-01 §Context: *"Network and Protect in local-direct mode are on the user's LAN at a private address. A remote HTTP server cannot reach `192.168.x.x`. **This is not a preference; it is routing.**"* That sentence is as true today as when it was written, and it is untouched by the single-tenant reframing. The reframing changes *who supplies the credential*; it changes nothing about *where the packets go*.

What changes is only the location of the obligation. ADR-01 read "remote" as "hosted somewhere else, by someone else," and under that reading routing was a blocker the product could do nothing about. A self-hosted deployment is placed by the operator, so routing becomes a **deployment constraint the operator can satisfy — and can also fail to satisfy silently.** That failure mode is worse than the one ADR-01 avoided, not better: a container in a cluster with no route to `192.168.0.0/16` starts cleanly, passes every startup refusal, answers `/readyz` with `200`, advertises the entire Network and Protect surface, and fails every call at connect time. Nothing in the product's own health model can tell the operator why, because readiness is deliberately process-local (FR-69, NFR-25) and must stay that way — a readiness probe that depends on a third party converts their outage into yours.

Two consequences follow, and both are requirements rather than advice:

- **The obligation is stated to the operator at startup, by name.** With the HTTP transport selected, at least one local-direct outbound host configured, and a non-loopback bind, the process warns on stderr and names every configured local host as one that must be routable from this process's network namespace (FR-79).
- **And it is stated again at the moment the symptom appears.** A startup warning is emitted once, four hundred log lines before the first failure, and the architecture concedes that an operator redirecting `2>/dev/null` loses every diagnostic it ships. That is not proportionate to a failure this ADR grades as *worse* than the one ADR-01 avoided, and the asymmetry was noted in review. So the control is doubled: **the first connect-time failure to a configured local-direct host emits one distinguished stderr line naming the routing obligation and the host** — `unifi-mcp: WARNING — no route to local console <host>. A local-direct console must be reachable from this process's network namespace; see UNIFI_LOCAL_HOST and "Deploying this" in README.md.` — emitted once per host per process, through the single sanitised emitter, at the moment the operator is looking. This is not a new requirement variable and not a new refusal; it is a diagnostic on an existing failure path.
- **Nothing may be certified on a deployment that cannot reach a console.** FR-74's parity harness must complete one successful read action per transport in the same run. Parity between two tool surfaces, proven on a runtime structurally unable to reach any console, proves that two lists match — it does not prove the product works, and asserting it there would be a green build certifying nothing. This is stated as an acceptance criterion precisely because the cheap version of the test is the one that omits it.

**Ground three — a doubled verification surface with no scaffolding. This ground has changed, and the change is what makes the decision available.** ADR-01 §Option D con: *"**Doubles the verification surface at exactly the moment there is no test scaffolding** (R-7), for a remote half that still cannot collect credentials."* That con bundles a permanent objection (two-of-everything, which survives and is accepted below) with a **conditional** one (no scaffolding), and the condition is what must be checked rather than inherited.

It is no longer "no scaffolding at all." M2's exit criteria (`docs/prd.md:340`) already schedule the harness — *"Test strategy exists as an actual harness … (R-7)"* — the seams it needs are designed rather than hoped for (architecture §10, which names every injection point, every counter and the teardown contract), and the harness is a named, owned deliverable of the Quality stage rather than an unassigned gap. That is a materially different position from ADR-01's, and it converts a hole into a schedule.

It is not, however, a discharged condition, and this ADR does not pretend otherwise. **The acceptance is therefore conditional and the condition is written into the Implications: this decision is not merged until the FR-74 / §11 harness exists.** That is the only formulation under which "the cost is paid down, not avoided" is a statement about the world rather than an aspiration. If the harness slips, the decision is not thereby wrong — it is thereby unmerged.

Beyond the three grounds, three facts about the shipped artefact bear on this decision:

- **The container is already a service, in every respect but the socket.** It is the vehicle the platform-team use case consumes, it is documented in `README.md:77-104`, and it already takes its credential from the environment because it installs with optional dependencies omitted — `keytar` is deliberately absent, so ADR-04's keychain-first path resolves to the environment on every start. The credential story for an HTTP deployment is therefore not new; it is the container's existing story.
- **Node is PID 1 in that image, with no signal handler installed.** An unhandled `SIGTERM` to PID 1 on Linux is ignored, so `docker stop` against today's image waits out its full timeout and then `SIGKILL`s. That is a defect in the shipped stdio artefact, independent of this decision, and this round fixes it for both transports (FR-80).
- **The verified SDK constrains the shape of any HTTP server built on it.** `Protocol.connect` throws on a second transport for one instance, so a multi-session server is one `McpServer` per session. The SDK supplies no session registry, no TTL, no cap, no eviction, no forced-termination API, and its DNS-rebinding options are deprecated with an Express-only replacement. Every one of those is work this repository owns, and the cost of owning it is part of what this decision is buying.

#### Options Considered

**Option A: Stay stdio-only; document the container as spawn-per-session and close OQ-09 as "no"**
- Pros: Zero new attack surface. No listener, no bearer secret, no session lifecycle, no drain, no `Host` or `Origin` validation to own. Every existing security property is preserved by construction. Costs nothing.
- Cons: Does not answer the request that reopened ADR-01. A platform team that wants one long-lived UniFi MCP service for several clients must either run one container per client session or build the listener themselves. It also leaves the PID-1 signal defect unfixed, because nothing forces the question. This option is a decision not to decide.

**Option B: Hosted multi-tenant streamable-HTTP** — *(rejected; unchanged from ADR-01)*
- Pros: The build skill's recommended default. No distribution problem.
- Cons: **The credential-collection blocker is entirely intact.** A hosted server still needs each user's UniFi key, Ubiquiti still publishes no OAuth, and Claude still does not support user-pasted bearer tokens. It also cannot reach any local-direct console for any user. Both of ADR-01's grounds apply to this option in full, and this ADR retires neither of them for it. Stays out of scope (Out of Scope #6).

**Option C: HTTP as the default transport, stdio available by flag**
- Pros: Matches the build skill's default posture. One obvious shape.
- Cons: **A regression for every existing user, delivered silently.** Dana, Marcus and Sam run stdio today. A default flip means the next `docker run -i --rm` produces a process that binds a port and reads nothing from stdin, and the failure is a hang rather than an error. It also inverts the security posture: the safe configuration would become the one the operator has to remember to ask for. IG-1 names this as the one regression this round cannot afford.

**Option D: Serving transport selected by configuration; stdio is the configuration default** *(chosen)*
- Pros: Existing users are untouched — not by convention but by construction, because with no serving-transport variable set the process behaves exactly as it did before this ADR existed, opens no listening socket, and `docker run -i --rm <image>` needs no additional arguments. The new shape is reached by typing one variable, which makes it an explicit operator act with an audit trail in the Deployment manifest. The core is genuinely transport-agnostic, so the addition is an addition. It also forces the PID-1 signal fix, because a drain is required for the HTTP shape and the same handler covers stdio.
- Cons: **Two deployment models means two security models, two configuration stories, and two things to get wrong** — ADR-01 Option D's own con, which was never a multi-tenant argument, and which comes true here. It adds twenty-two configuration variables, a bearer secret, five startup refusals, a session lifecycle, a drain sequence, and `Host`/`Origin` validation this repository must own because the SDK's is deprecated. It doubles the verification surface (R-7) at a moment when the test harness for it does not yet exist. The cost is paid down, not avoided: every one of those controls is written to **refuse to start** rather than start unsafely.

**Option E: Selection by command-line argument or container `CMD` rather than by configuration**
- Pros: Arguably more discoverable — `--http` reads better than an environment variable in a shell.
- Cons: **`CMD` is overridable and argv is not where this product's configuration lives.** Every other setting in this server is a `UNIFI_*` variable validated by one validator that refuses unknown keys; a transport selected by argv would be the only setting outside that mechanism, and the only one the five startup refusals could not see. A container `CMD` default is worse still: a `docker run <image> --http` typed by someone reading a stale README would bind a port with no bearer secret configured, and the `ENTRYPOINT` must stay exec-form with **no top-level `CMD`** so that the stdio invocation keeps working unchanged. Rejected on both grounds.

#### Decision

**Option D. The serving transport is selected by configuration, and the configuration default is `stdio`.**

Specifically:

- **`UNIFI_MCP_TRANSPORT` selects the serving transport**, accepting `stdio` (default) or `http`. **The default is a configuration default, not an argv default and not a container `CMD` default.** With no serving-transport variable set the process reads MCP frames from stdin, writes them to stdout, and opens no listening socket — asserted portably by a `net.connect` to the default bind and port being refused with `ECONNREFUSED`. The `Dockerfile` keeps its exec-form `ENTRYPOINT` and declares no top-level `CMD`.
- **The production entrypoint activates exactly one serving transport per process.** That rule governs the entrypoint. It does not govern the runtime: test code constructs the shared runtime directly and connects two `McpServer` instances to two transports in one process, which is the only reading the SDK permits in any case (FR-62, FR-74, RC-2). **Corrected in Revision 2:** that two-transport process proves **advertisement** parity and nothing else. A runtime carries exactly one `activeSurface`, and the outbound client's write gate reads the write set resolved for that one surface — so a single process cannot enforce two surfaces' gates at once, and the parity harness must not be read as claiming it does. The execution gate is asserted in a separate single-surface run, and the harness builds one runtime per surface where the *gate*, rather than the *advertisement*, is under test.
- **The shape is single-tenant and self-hosted.** One operator, one process, one set of credentials, one shared secret. There is no user model, no tenant model, and no per-user identity — the transport authenticates the *caller*, never a *user*.
- **The default bind is `127.0.0.1` and the default port is `8787`.** Widening the bind is an explicit operator act. **"Loopback" is a closed predicate, not a word:** exactly an IPv4 literal in `127.0.0.0/8`, the IPv6 literal `::1`, and the IPv4-mapped forms of the first. `0.0.0.0`, `::`, every hostname including `localhost`, and every value the parser does not recognise are **not** loopback. Two of the five startup refusals and the whole of NFR-23 turn on this predicate, so it fails closed: an unrecognised bind value is a startup error naming `UNIFI_HTTP_BIND`, never a value the predicate judges.
- **`UNIFI_HTTP_AUTH=none` is the only sanctioned route to an unauthenticated listener, and it is designed rather than implied.** Authentication resolves at configuration load into one of two shapes — bearer with a non-empty set of slot digests, or none — and the second is refused outright on any non-loopback bind (refusal (e)). The comparator cannot be reached with an empty slot list, because the empty case is not representable in the type it takes; there is no fail-open branch to write. `none` is a startup warning on every start, naming the exposed population.
- **Streamable-HTTP only**, with the SDK's `enableJsonResponse` left at its default (SSE mode) and `keepAliveMs` set explicitly from configuration rather than inherited.
- **stdio's *interface* gains nothing and loses nothing; three things about stdio do change, and pretending otherwise was wrong.** *(Corrected in Revision 2.)* No inbound surface, no listener, no configuration requirement, no new operator-facing message and no endpoint changes for a stdio user: every message, refusal, warning, log line and endpoint introduced by this ADR is inert unless the HTTP transport is selected. What does change, in the artefact stdio users install, is stated rather than glossed:
  1. **Signal disposition.** `SIGTERM` and `SIGINT` are now handled on both transports. This is a deliberate fix to the PID-1 defect below, not a side effect — but it is a behaviour change, and for an interactive `claude mcp add` session it is user-visible. So the escalation is defined for what an interactive user actually does: **the first signal drains; a second `SIGINT` exits `130` immediately and a second `SIGTERM` exits `143`.** Exit `75` is reserved exclusively for drain-deadline expiry and is never produced by an operator pressing Ctrl-C twice, because a code that means "the 35-second derivation was wrong" must not be emitted by the most common human action in the system.
  2. **`src/http/client.ts` and `src/http/ratelimit.ts` ship in the MCPB bundle**, so the lifecycle affordances — the timer-handle sets, the closed checks at the top of `acquire()` and `consume()`, the abort wiring — execute on stdio, on every request. They are small and additive; they are not inert.
  3. **The declared SDK range narrows to `~1.30.0`** in the same artefact.
- **Graceful shutdown is a POSIX-signal feature.** *(Added in Revision 2.)* On Windows `process.on('SIGTERM')` registers silently and never fires; termination is unconditional. A Windows deployment of the HTTP transport therefore has **no** graceful shutdown: no drain, no terminal frames, no agent destruction, no exit 75, and the FR-70 and NFR-27 guarantees do not apply. CI's Windows leg asserts the drain *state machine* through the directly-callable drain function and must not be read as asserting the guarantee. **Windows is a supported development and stdio platform; it is not a supported HTTP deployment target**, and that is recorded here rather than discovered when a service fails to drain.

**OQ-09 is resolved: yes, single-tenant self-hosted only.** The demand-side half of that question — whether cloud-only users are a meaningful share — is *not* answered by this decision and is not claimed to be. This question was closed on a stakeholder request for a deployment shape, not on the usage evidence its own resolution path asked for; v1 has not shipped and no usage data exists. The demand measurement is folded into G-4's third install shape.

**ADR-01's Option D is partially adopted, and its text is amended accordingly (E-36).** What was rejected and stays rejected is the hosted, multi-tenant half — it still cannot collect each user's key, so it still buys nothing that works. What is adopted is the narrower shape ADR-01 did not distinguish at the time. The separability that ADR-01 conditioned its rejection on stops being an observation about the codebase and becomes an obligation on this change: the HTTP entrypoint changes `src/index.ts`, adds `src/serve/`, and extends `src/config.ts` and `package.json`, and it must not change `src/tools/*`, `src/registry/*`, `src/safety/*` or `src/network/*`. Two files under `src/http/` are named, bounded exceptions — `client.ts` and `ratelimit.ts` may change **only** to add lifecycle affordances, with no behavioural change to request construction, retry policy or rate-limit arithmetic — because a graceful drain that terminates within a derivable deadline is impossible without them, and a decision record that claimed otherwise would be asserting a falsehood the implementation would have to expose.

##### Binding to a port changes who the caller is

This is the substantive security consequence of the decision and it is stated here rather than left to a risk row.

On stdio the caller population is **whoever can already run the process**. That is not a security control the product implements; it is a property of the operating system, and it is total. A caller who can spawn the server can already read its environment, its configuration and its credential file — every asset the server holds is already theirs before the first MCP frame. Authentication on stdio would protect nothing, which is why there is none.

With a listener the caller population becomes **anyone who can reach the port**. That set is defined by network topology rather than by process ownership, an operator does not choose it explicitly, and it is not observable from inside the process. The change is not incremental. It is a different threat model, and every control in this round exists because of it:

- **The failure is asymmetric, and that is what makes it dangerous.** Binding too narrowly fails loudly, as `connection refused`, and is fixed by one variable. Binding too widely **works perfectly** and is reachable by the whole network segment. The mistake with the worse outcome is the one with no symptom.
- **The default bind is a speed bump, not protection, and inside a container it is not even that.** `127.0.0.1` inside a container's network namespace is reachable only from inside that container, so a containerised deployment with the default bind is unreachable by design — the operator's *first* action is to widen it, and the loopback default's real function is to make that widening a deliberate, visible edit rather than an inherited one. It must not be described, in the README or anywhere else, as a security control that survives containerisation, because it does not.
- **`Host` allow-listing is a DNS-rebinding control that protects browsers. It is not an access control.** The `Host` header is entirely caller-supplied, so it offers no protection whatsoever against a direct attacker; it exists to stop a victim's browser being used as a proxy into the operator's network. Treating it as defence in depth is the seductive error, and the ordering decision below is where it does real damage. `Origin` is rejected outright for any value rather than allow-listed, because a conforming MCP client is not a browser and sends none — and an allow-list would be inert anyway, since the server emits no CORS headers, so a browser whose request was accepted still could not read the response.
- **The two controls that actually bound the exposure are the bearer secret and network-layer policy** — a firewall, a Kubernetes `NetworkPolicy`, or a reverse proxy that does not forward. Everything else raises cost.
- **Authentication is evaluated before everything else, and to an unauthenticated caller every rejection is byte-identical.** Any check that precedes authentication and can produce a *different* response is an oracle. `Host` first would let a stranger enumerate the allow-list by status differential, at zero cost, using a control that bought no access protection to begin with.
- **The trust boundary is written down, not implied.** ADR-01 never needed one; this decision does. The assets are the operator's UniFi API keys, the inbound shared secret, session identifiers, and the ability to invoke actions against the operator's estate. The trusted side is the process and its configuration; the untrusted side is every inbound socket, every header including `Host` and `Origin`, every request body, and every `Mcp-Session-Id` a caller presents. The entry points across the boundary are the MCP endpoint, `/healthz` and `/readyz`. NFR-32 obliges this to be maintained as `docs/prd.md` §5.15.3 with the controls at each entry point and the requirement that owns each — and, explicitly, the **non-defences**, so the gaps are decisions rather than oversights.

##### What is deliberately not defended against

Stated here so that a security review has something to review, and so that no reader mistakes silence for coverage.

- **A caller holding the shared secret is fully trusted.** There is no per-user identity and no per-request authorisation. Anyone with the secret can drive every enabled action. Authorisation granularity is by configuration and is fixed for the lifetime of the process.
- **TLS is terminated upstream.** The listener speaks plain HTTP. An operator who exposes it beyond loopback without a proxy broadcasts the bearer secret in the clear, voiding every authentication control above. The startup warning on a non-loopback bind is the only mitigation the product ships.
- **The authentication-failure throttle is bypassable by source rotation**, and its bounded table means a rotating attacker can evict the entries of genuinely throttled sources. It raises cost against a single source; it is not what protects the secret. The 32-character minimum and restricted network reach are.
- **Behind a reverse proxy — the recommended shape, because it is the only way to get TLS — the throttle protects nothing.** *(Added in Revision 2.)* Every request arrives from the proxy's address, so the source key collapses to one value for the entire caller population and per-source counting has nothing to count. The throttle is therefore **inert** in that topology, and it is inert **by design rather than by accident**: a throttled source is still authenticated normally and is still served if its secret is valid, so a stranger who trips the shared key cannot lock out the legitimate client. That property is bought deliberately, and the alternative — refusing a throttled source before examining its credential — was rejected precisely because it converts this control into a one-line remote denial of service against the only legitimate caller. No `X-Forwarded-*` header is consulted, for the throttle or for anything else.
- **The floor on the shared secret is a length floor, not an entropy floor.** *(Added in Revision 2.)* Thirty-two identical characters satisfy it. Slot digests are unsalted SHA-256, so a digest recovered from a heap dump or a core file is offline-attackable at whatever entropy the operator's secret actually carries, not at 256 bits. The README's rotation guidance must recommend a CSPRNG-generated value; the product does not measure one.
- **Any caller holding the secret — or one buggy client — can occupy every session slot and deny the operator's own client.** *(Added in Revision 2.)* Refusing at the cap rather than evicting a live session is the right decision and is kept, but it has a mirror image that was argued in only one direction: keeping thirty-two sessions warm costs one request per session per five minutes, needs no malice, and a client that never sends `DELETE` and reconnects on every restart does it by accident. There is no per-source session cap in this round, no admin termination endpoint, and — since sessions are in-process and rotation is restart-based — **the operator's only remedy is to restart the process**, which drops every session including the legitimate ones. Recorded because the buggy-client case needs no attacker at all.
- **The probe connection headroom raises the cost of probe starvation; it does not close it.** *(Corrected in Revision 2 — the previous revision described this as closed.)* The eight reserved connections are reserved by *route*, and "probe" is a property of the request string rather than of the caller, so probe-shaped keep-alive traffic can occupy them. A per-source cap of one headroom connection is specified, which defeats the single-source version completely; a distributed attacker with eight source keys is not defeated by it. The control that closes the attack is network reach.
- **The `auth=none` mode on loopback is a real widening over stdio, not an equivalent.** *(Corrected in Revision 2 — the previous revision claimed the loopback caller population equalled stdio's, and it does not.)* On stdio the caller population is whoever can already run the process, which is a genuine property of process ownership: such a caller can already read the environment, the configuration and the credential file, so authentication would protect nothing. **A loopback socket carries no uid check of any kind.** Its caller population is every local uid that can open a TCP connection to `127.0.0.1` — every other account on a shared workstation, jump host or build machine, every container sharing the host network namespace, and every process of every user, including ones that could not spawn the server and could not read its secrets. `UNIFI_HTTP_AUTH=none` therefore hands the full enabled tool surface, backed by a live UniFi key, to any local account. It remains available because the operator must type the opt-out word and because it is refused outright off loopback — but it is accepted on those terms, and the startup warning names the exposed population so the operator reads the true statement at the moment of the decision.
- **The composed unauthenticated surface is a reliable product fingerprint.** Two probe endpoints with fixed bodies identify the host as a UniFi MCP instance holding a live UniFi key, with zero credentials presented. That is the price of serving orchestrator probes unauthenticated, which is a deliberate trade.
- **No brute-force alerting primitive ships.** Detection is the operator's, built by grepping the per-request log line. There is no metrics endpoint and no security-event stream.
- **An attacker with read access to the host's process table or the Docker socket can recover the secret** before the environment scrub completes, and can read it from `docker inspect` output if it was supplied with `-e`. File delivery and `secretKeyRef` exist because of this.
- **The uniform rejection is byte-identical, not time-identical.** No constant-time floor is specified across rejection classes; one would add latency to every rejection for a signal that is noisy across any real network.

##### Recommended defaults, ratified

Inherited from the delivery brief and the operator interface contract, examined and adopted unless noted:

- **Bearer comparison: SHA-256 both operands, then `timingSafeEqual` on two 32-byte digests, against every configured slot with no short-circuit and the results OR-accumulated.** Hashing first is not decoration: `timingSafeEqual` throws on a length mismatch, so comparing raw operands would make the presented length an oracle and would turn a wrong-length guess into an exception rather than a rejection. Comparing all slots unconditionally keeps the number of configured secrets unobservable.
- **The HTTP write gate is a single narrowing of the resolved write-enablement set at configuration load.** It inherits both existing enforcement points — tool-list visibility and the outbound-request refusal — and adds **no third check in the transport layer**, and *(corrected in Revision 2)* **no third check anywhere else either.** The previous revision forbade a transport-layer check and then, one paragraph later, specified an entrypoint-owned handler that refused gate-narrowed calls before the outbound client was reached. That was a third enforcement site by FR-71's own two-value classification, and it is deleted. The problem it was added to solve is real and is solved differently: when the effective HTTP write set is *non-empty but narrowed*, the write tool is advertised and a call naming a service outside the set reaches the existing outbound gate, whose refusal message is amended to name `UNIFI_HTTP_ALLOW_WRITES` alongside `UNIFI_ENABLE_WRITES` — a message change inside an already-open file, admitted by name in the diff-scope check rather than by silence. When the effective set is *empty*, the tool is not advertised at all and the honest answer to a call is the SDK's own refusal of a tool it does not have registered — *(Revision 8: this read "the SDK's own method-not-found", which names a channel `@modelcontextprotocol/sdk@~1.30` does not use. It throws `McpError(ErrorCode.InvalidParams)` and catches its own throw, returning an `isError` tool result rather than any JSON-RPC error frame. The architectural point is unchanged and is the reason this bullet exists: the refusal comes from the dispatcher, not from a third enforcement site. See FR-71 AC 1b, amended for the same defect, UAT defect D-08.)* — and the operator-facing signal for that state is the startup warning that fires on every such start, which is why that warning exists.
- **Default port `8787`; probe paths `/healthz` and `/readyz` as fixed constants that no variable can move.** Startup refuses outright if the configured MCP path normalises onto either, because otherwise the probe exemption swallows the MCP endpoint and serves the whole tool surface unauthenticated.
- **Authentication is evaluated for every non-probe request, and the throttle gates the *response* rather than the *work*.** *(Revised in Revision 2.)* The probe branch is evaluated **before** the throttle, so a source key at its ceiling still receives `200 ok` on `/healthz` — the previous ordering let one throttled source key produce `429` on a liveness probe, and a failing liveness probe restarts the pod, so the rate limiter would have restarted the service it protects. And the `429` is emitted only when the request has *also* failed authentication, so a caller holding the correct secret is served regardless of the throttle. The cost is one SHA-256 per request from a throttled source, over an input already bounded by `UNIFI_HTTP_MAX_HEADER_BYTES`; the thing bought is that neither an orchestrator probe nor the legitimate client can be locked out by a stranger, in any topology.
- **Shutdown: a 5-second pre-drain hold, then the ordered drain, inside a 35-second deadline; documented minimum orchestrator grace period 50 seconds.** *(Revised in Revision 2.)* The listener is **not** closed at t0. Readiness flips to `draining` immediately, and the listener stays open for five seconds answering new MCP requests with the `503` drain body and `Connection: close`, because SIGTERM and endpoint withdrawal are concurrent and independent — a control plane keeps routing new connections to a terminating pod for seconds after the signal, and closing the socket at t0 turns every routine rolling deploy into client-visible connection refusals with no server-side trace. The residue after the hold is unchanged and is a **maximum over states, not a sum**: an action is in exactly one of five states at any instant, and with the limiter refusing new acquisitions, the in-progress hop abandoned, the in-progress backoff abandoned and credential resolution failed rather than awaited, the residue is one in-flight attempt at 25 seconds. So the budget is `5 + max(0, 0, 0, 25) = 30` seconds, and the 35-second deadline — unchanged, because it is a published default in a closed variable family — now carries a 5-second margin rather than 10. The grace period of 50 seconds is likewise unchanged and still sits 15 seconds above the deadline. **The rate limiter stopping admission on SIGTERM is what makes the deadline derivable at all**; without it the worst case for a single ordinary read action is 136.8 seconds plus an unbounded queue term, and no honest deadline exists. The margin narrowing is the price of not dropping connections on every deploy, and it is stated so that a later change to either number is made against a written derivation.
- **`UNIFI_CONNECTOR_TIMEOUT_MS` is the one operator-settable value that can invalidate the derivation, and it warns.** It defaults to 25 000 and has no ceiling; raised to 60 000 for a slow local console — an entirely reasonable act — it guarantees that every drain with one in-flight request hard-stops. Startup emits a warning naming `UNIFI_CONNECTOR_TIMEOUT_MS` and `UNIFI_HTTP_SHUTDOWN_DEADLINE_MS` whenever the pre-drain hold plus the connector timeout leaves less than the stated margin. This is a cross-field check over existing variables, so the closed family is untouched.
- **Readiness and drain are answered synchronously from process-local state.** `/readyz` reads one enumerated value from a plain object: `starting`, `ready`, `draining`. It performs no I/O, awaits nothing, reaches no third party, validates no key, consults no keychain and repeats no startup work — and it answers correctly with all outbound network blocked. `/healthz` reports bind-liveness only and **does not change during drain**, because a liveness probe that fails while the process is shutting down gets the container killed mid-drain and converts a graceful shutdown into a `SIGKILL`.

##### Concurrency budget for the shared outbound bucket

Sessions contend for one set of token buckets, because the buckets model a limit the UniFi console enforces per console rather than per client. Sharing the outbound client is therefore **correctness, not economy**: per-session clients would multiply the outbound rate a console sees by the number of connected clients and produce exactly the self-inflicted 429s the limiter exists to prevent.

The limiter chains waiters FIFO, so queue depth compounds. At the published Connector figure of 100 requests per minute a single hop waits at most 600 ms, and the saturation ceiling never fires. The bound that matters is therefore the queue, and the session cap is what bounds it: with `UNIFI_HTTP_MAX_SESSIONS` at its default of 32 and one outbound call in flight per session, the last waiter is admitted after roughly 19 seconds — inside the 25-second per-attempt deadline, which is not consumed by queueing because the per-attempt `AbortController` is created after acquisition resolves. **The session cap is a reliability control, not only a memory bound, and lowering the outbound rate limit or raising the session cap moves the tail wait linearly.** No requirement caps concurrent outbound calls *within* one session, so the derivation holds only at one call per session; that residual is recorded rather than papered over, and the operator's lever is the session cap.

##### An in-flight outbound call whose session closes

Unspecified before this ADR, and decided here: **the outbound call is not cancelled. It runs to its own per-attempt deadline and its result is discarded.**

Closing a session runs the SDK's protocol teardown, which aborts every in-flight request handler's `AbortController`. A handler that observes its signal stops. But the outbound client accepts no `AbortSignal` — its public `request()` takes none, and plumbing one through would require changing `src/tools/handlers.ts`, which sits inside the untouchable set. Adding a caller-facing signal to `request()` is also not a lifecycle affordance, so it falls outside the bounded exception granted to `src/http/client.ts`. The two halves cannot be done separately and neither can be done in this round.

The consequence is bounded and is stated so nobody discovers it: a caller that opens and abandons sessions can leave up to `UNIFI_HTTP_MAX_SESSIONS` outbound calls running that nobody will read, each capped at 25 seconds per attempt and each having already spent its rate-limit token against the console's budget. The late response is dropped silently by the transport. **The remedy is named for a later round** — add an optional `signal` to `UnifiClient.request()` and thread it from `createHandlers` through to `extra.signal`, together, in a round that reopens `src/tools/*` — and is not attempted here, because doing half of it changes a protected directory for no benefit.

#### Implications

- **stdio is unchanged, and that is a tested property rather than an intention.** With no serving-transport variable set, a transport-activation counter reads `1` for stdio and `0` for HTTP, no socket is opened, and the container's stdio invocation needs no arguments.
- **The second deployment model brings a second security model and a second configuration story**, exactly as ADR-01's Option D warned. Accepted knowingly. The cost is paid down by making the second model refuse to start rather than start unsafely: five startup refusals, each naming the variable that fixes it, all executing before any listener binds.
- **This repository now owns `Host` and `Origin` validation as a security control** — implemented in-repo against the raw request objects and unit-tested as pure functions — because the SDK's options are deprecated and the shipped replacement is Express-only. An SDK upgrade must re-verify both behaviours before merge (R-16).
- **The session registry, its identifiers, its cap, its TTL, its sweep and its termination path are ours in full.** The SDK provides none of them at any layer, and a design that waits for an SDK callback to clean up after an eviction leaks every abandoned session — the callback fires on client `DELETE` only.
- **Signal handling becomes mandatory for both transports.** The container's `ENTRYPOINT` is exec-form with no init process, so the server is PID 1 and owns its own signal disposition. Handlers are installed as the first action of `main()`, before any asynchronous startup work.
- **`src/http/client.ts` and `src/http/ratelimit.ts` gain lifecycle affordances and nothing else**, enforced by a CI diff-scope check that treats any hunk touching URL assembly, header construction, attempt counting, backoff computation, token accounting or refill arithmetic as a failure. *(Revised in Revision 2.)* "And nothing else" is honoured by **enumerating** the consequential hunks rather than by asserting there is one: the drain-abandonment race around credential resolution, the drain check placed *after* the existing write gate so the gate keeps its precedence, the `transportError` arm that distinguishes a drain abort from a 25-second timeout, the preserved `retryAfterSeconds` on the shutdown rejection, and the amended write-gate refusal message. Each is admitted by matched expression in the diff-scope check, so admitting it is a recorded decision rather than a loophole. **`src/credentials.ts` becomes a third named exception**, for one optional field on `CredentialStoreOptions` that lets a test suppress the OS keychain — without it, `keytar` is installed by `npm ci` on two of the three CI platforms and the requirement that the real credential path be exercised would drive a developer's real login keychain.
- **This decision is not merged until the FR-74 / operator-contract §11 harness exists.** ADR-01's third ground against Option D was a doubled verification surface with no scaffolding; that ground has moved but is not discharged, and this is the condition under which "the cost is paid down, not avoided" is true rather than aspirational. The harness is M2's exit criterion already (`docs/prd.md:340`) and the seams it needs are designed; what is added here is the coupling.
- **Container-level assertions must gate pull requests before they can be claimed.** Six requirements delegate assertions to the container workflow, which today runs post-merge only, so those assertions gate nothing. A pull-request job that builds the image into the runner's own daemon and runs the assertions **in that same job** is part of this change rather than a follow-up — a separate job with `needs:` finds an empty daemon, which is the identical bug one layer down.
- **The image stops asserting that it does not listen on a port.** `EXPOSE 8787` lands as inert metadata, the header comment block and the `LABEL … description` are rewritten to describe both transports, the `ENTRYPOINT` stays exec-form with no top-level `CMD`, and the `HEALTHCHECK` becomes transport-aware so that under HTTP it exercises the listener instead of re-parsing four OpenAPI specs in a second interpreter every sixty seconds.
- **Exit codes are a closed vocabulary and each means one thing.** `0` clean shutdown by natural drain; `1` a configuration refusal or a listen failure; `70` a drain initiated by an uncaught exception or unhandled rejection; `75` **only** drain-deadline expiry; `130` and `143` an operator-forced second `SIGINT` or `SIGTERM`. Exit 75 during termination means the drain hit its deadline, is expected under pathological conditions, and must be excluded from crash alerting; a *recurring* 75 is the signal it was designed to be and re-opens the derivation.
- **The declared SDK range narrows to `~1.30.0`** in the same commit that introduces the serving transport, because every behaviour this decision relies on was verified against 1.30.0 and the manifest currently permits versions in which the transport class does not exist.
- **The routing obligation is the operator's, permanently.** It is warned about at startup, warned about again on the first connect-time failure to a configured local-direct host, documented next to the bind guidance, and enforced in the parity harness by requiring a real read action to succeed on both transports in the same run. The doubling is deliberate: a startup warning alone is emitted once, hundreds of lines before the symptom, and can be lost to `2>/dev/null`.
- **The default bind is the most likely operational bug in the feature, so it warns too.** A loopback listener inside a container's network namespace is unreachable by its own pod's probes, and the failure has no error to log because no request arrives. With the HTTP transport selected and a loopback bind the process emits one stderr warning naming `UNIFI_HTTP_BIND` and stating that a container or pod probe cannot reach it. A refusal would be wrong — loopback is legitimate outside a container — but silence turns an invisible failure into a support case, and one line turns it into a `docker logs` grep.
- **Ruled out, and still ruled out after this ADR:** any **hosted, multi-tenant** deployment — the credential-collection blocker is unchanged (Out of Scope #6); any browser-only usage; **in-process TLS termination**, because certificate acquisition, renewal and rotation are solved in the layer above and reimplementing them would add a certificate lifecycle to a process whose entire security model is one operator, one secret, one loopback bind (Out of Scope #14); **OAuth, OIDC or any per-user identity**, because the transport authenticates a caller and not a user, and UniFi publishes no OAuth to federate with even if one were wanted (Out of Scope #15); **multi-replica deployment**, because session state is in-process and, more fundamentally, because each replica carries its own token buckets, so N replicas multiply the outbound rate a console sees by N and produce the self-inflicted 429s R-2 was opened against (Out of Scope #16); **stream resumability**, because it requires durable event storage with its own retention, ordering and eviction design — a second stateful subsystem in a server that otherwise holds no state, for a failure mode a retry already covers (Out of Scope #17); **the deprecated HTTP+SSE two-endpoint transport**, because supporting it would double both the inbound surface and the security surface, since `Host` and `Origin` validation are owned in-repo and would have to hold on both (Out of Scope #18); and **per-request RBAC over the action surface**, which presupposes the per-user identity ruled out above — the two stand or fall together (Out of Scope #19).
- **Not shipped and recorded as a gap rather than an omission:** metrics, tracing and an observability endpoint. The server emits one structured log line per request and nothing else, and the probe endpoints deliberately carry bare status, so session count, queue depth, rate-limit waits and rejection rates are not externally visible in 1.0 (Out of Scope #20).
- **OQ-09 closes.** OQ-15's environment-exposure question narrows but does not close, because file delivery and the environment scrub reduce the window rather than remove the exposure.

#### Review Date

Reopen the **hosted multi-tenant** question — which this ADR does not touch — under ADR-01's original triggers: when either (a) Ubiquiti publishes an OAuth flow for developer API access, or (b) post-1.0 usage shows cloud-only users are the dominant segment, whichever comes first.

Reopen **this** decision on any of three triggers, none of which is a date:

1. **An SDK release that changes streamable-HTTP teardown, session handling, or the deprecated DNS-rebinding surface.** The floor is pinned at `~1.30.0` and a canary reports drift; a bump arrives as a pull request that must re-verify `Host` and `Origin` behaviour before merge.
2. **Evidence that the shutdown deadline is wrong in practice** — any observed `SIGKILL` at the documented 50-second grace period re-opens the derivation, not merely the number.
3. **A second replica being asked for.** That is not a configuration change; it re-opens the shared-outbound-bucket decision and Out of Scope #16 together, and neither can be answered alone.

## 12. Handoff to `mcp-server-dev:build-mcp-server`

*Historical note — this section is retained as the record of the design brief handed to `mcp-server-dev:build-mcp-server`, not as a pending instruction. The skill was invoked and the server was scaffolded at commit `7fd3bbd`. The paragraph below describes the shape as originally briefed, corrected on 2026-08-01 for the operation count, the blocklist membership, and the serving transport; where it differs from Sections 5, 6 and 11, those sections govern.*

**UniFi MCP is a server that defaults to stdio transport, distributed as an MCPB bundle and as a container image, and that can additionally be run as a single-tenant self-hosted streamable-HTTP service (ADR-05)** — stdio rather than hosted remote streamable-HTTP because Network and Protect in local-direct mode sit at private LAN addresses that no hosted server can route to, and because UniFi's auth is a long-lived user-supplied API key with no OAuth and no supported `static_bearer` collection path, so a hosted multi-tenant deployment has no way to obtain a user's credential — a blocker that does not apply to a single-tenant self-hosted deployment, where the operator supplies their own key by environment variable or by file exactly as on stdio; the codebase keeps the transport layer separable, and the HTTP entrypoint is required to be an addition under `src/serve/` rather than a rewrite, leaving `src/tools/*`, `src/registry/*`, `src/safety/*` and `src/network/*` unchanged while extending `src/index.ts`, `src/config.ts` and `package.json`, and while making **bounded lifecycle-only additions** to `src/http/client.ts` and `src/http/ratelimit.ts` — the two files that today expose no way to stop a wait, cancel a backoff or release a pooled agent, and without which the shutdown deadline of FR-70 is not derivable. Those two files change to gain affordances, never behaviour: request construction, retry policy and rate-limit arithmetic are unchanged, and a CI diff-scope check enforces the distinction. **The tool pattern is hybrid search + execute**, because the four vendored OpenAPI specs total 168 operations — 5.6 times past the 30-operation threshold at which one-tool-per-action is prohibited — with exactly five operations promoted to dedicated read tools (`unifi_list_consoles`, `unifi_list_sites`, `unifi_list_devices`, `unifi_list_clients`, `unifi_list_cameras`), a `unifi_search_actions` tool mapping natural-language intent to directly-usable action IDs and schemas, and **two** separate execution tools — `unifi_execute_action` for reads and `unifi_execute_write_action` for state-changing operations, separate because a single tool accepting both is auto-rejected at directory review — all under a ≤ 3,000-token advertised-schema budget with per-API exposure filtering so a user without Protect gear pays nothing for Protect schemas. **The framework is the official TypeScript SDK (`@modelcontextprotocol/sdk`) on Node**, the skill's default, chosen because the MCPB bundling requirement is a Node-first path, `keytar` is the named credential-storage module for local servers, and OpenAPI 3.1's JSON Schema 2020-12 lands natively in the TypeScript ecosystem — with no Python library to wrap and no stated language preference, neither of FastMCP's stated triggers applies. **Auth is user-supplied UniFi API keys sent as `X-API-Key`, entered at install time through MCPB manifest fields marked `sensitive: true` or through environment variables, resting in the OS keychain via `keytar` with an environment-variable fallback for headless and CI use and never in plaintext on disk, never collected via elicitation, and never present in any tool result, `structuredContent`, error message, or log** — with multi-credential resolution by request target (one cloud key for Site Manager, Mobility, and all Cloud Connector traffic; zero or more local console keys each bound to a configured host), a documented post-generation auth-injection step for Network and Protect because their specs declare no `securitySchemes` at all, Mobility's `mobility` app scope plus `read:mobility`/`write:mobility` carried as action metadata surfaced in the 403 recovery hint, and a read-only default posture in which `unifi_execute_write_action` is absent from `tools/list` until an explicit configuration flag is set — two independently-set flags on the HTTP serving transport (FR-71) — with an enforced Never-Ship blocklist that is not overridable in any configuration: five whole-operation blocks (device adoption; un-adoption, which factory-resets an online device as a side effect; network deletion; wifi-broadcast deletion, which is how the spec models a WLAN; and Protect `disable-mic-permanently`) plus two withheld request-body variants (`RESTART` and `POWER_CYCLE` on the generic device- and port-action endpoints). Firmware upgrade, standalone factory reset, and site deletion match no operation in any vendored spec and are retained as forward-looking policy only (FR-46, OQ-11).

Section 6 (NFR-01 … NFR-10) restates the skill's non-negotiable constraints as separately testable requirements; treat that table as the acceptance checklist for the scaffolded server. Section 5 is the functional specification. Verification uses MCP Inspector (`npx @modelcontextprotocol/inspector`, and `--cli` in CI) per FR-60 — no bespoke MCP harness.
